# Summary of changes for run f5c197cf-a37d-4eec-a0f8-5189709ea96f
I reviewed and audited the seven Solidity contracts in the repository (`CreatorOracle.sol`, `CreatorGaugeController.sol`, `Registry4626.sol`, `CreatorPayoutRouter.sol`, `VaultShareBurnStream.sol`, `LinearVesting4626.sol`, `CreatorCoinPolicyController.sol`) with a manual, line-by-line pass focused on access control, arithmetic/accounting invariants, reentrancy, oracle-manipulation/price integrity, external-call safety, cross-chain message handling, and centralization. The full write-up is in `AUDIT.md`.

Key findings:

- **M-1 (Medium, CreatorOracle):** `_sequencerIsUp()` applies the 2-hour `MAX_STALENESS` bound to the L2 sequencer uptime feed. That feed only updates on status changes, so after ~2h of normal uptime the check reports the sequencer as "down" and fails closed — freezing `getEthPrice`, `updateAssetPriceFromTWAP`, the auto-update path, and V3 USD conversion (and downstream gauge WETH processing) whenever the optional sequencer feed is configured.
- **M-2 (Medium, VaultShareBurnStream):** failed vault burns advance `burnedActive` and record shares in `failedBurnAccumulator`, but those shares physically remain and are not included in the "accounted" set, so permissionless `syncUnaccounted()`/`checkpoint()` re-queue them — double-counting. This can leave `failedBurnAccumulator` permanently non-zero, break `recoverFailedBurns`, and eventually hit the cap and DoS the drip.
- **Low:** missing sequencer post-recovery grace period (L-1); burn-stream authorization/recovery bootstrapped only via `msg.sender == vault`, a fragile integration assumption (L-2); keeper can make arbitrary-calldata calls to allowlisted swap targets (L-3); owner `emergencyWithdraw` can drain non-protected in-flight tokens (L-4); vesting pre-`seed()` release can under-allocate the schedule (L-5).
- **Informational:** misleading "burned" events on failed burns, extreme-tick precision boundary in `tickToPrice`, `uint16` chain-id in `Registry4626.setLzConfig`, a wrong error name in `seed()`, and broad owner/keeper powers that warrant a timelock/multisig.

The report also records what held up well (oracle price-deviation bounds and robust Chainlink reads, LayerZero source-EID/timestamp guards, consistent `nonReentrant` + `SafeERC20` + approval resets, owner-less burn custody, registry reverse-mapping hygiene, gauge MEV hardening), each with recommendations.

Each finding in `AUDIT.md` includes the affected code, impact, and a concrete remediation. I also noted that the included Lean/Mathlib scaffold (`RequestProject/Main.lean`) is an empty stub with no specifications; I did not add formal proofs, but flagged candidate invariants (burn-stream share conservation and the fee-split BPS sum) that could be formalized if wanted.
