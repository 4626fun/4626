## Regeneration + verification

**Important:** `contracts/vault/CreatorOVault.sol` on `main` may already carry `CreatorOVaultModuleStorage.v3` (impairment stack). Do **not** regenerate `frontend/src/deploy/bytecode.generated.ts` from that head while v1.13.0 greenfield remains on **v2** — regeneration would embed the v3 fingerprint and break live Phase 1 (`InvalidModuleAddress`). Keep the committed v2 `DEPLOY_BYTECODE` / manifest until a coordinated v3 store cutover.

```bash
forge build --skip test --skip script
./script/generate_bytecode_manifest.sh v1.13.0
./script/generate_frontend_deploy_bytecode.sh
pnpm -C frontend typecheck
pnpm -C frontend exec tsx scripts/ops/verify-v1130-deploy-versioning.ts
pnpm -C frontend exec tsx scripts/ops/verify-bytecode-store-seeded.ts
pnpm -C frontend exec tsx scripts/ops/verify-batcher-pipe-a-readiness.ts
./test/current-release-target-guard.sh
```

Explicit manifest override:

```bash
BYTECODE_MANIFEST=../../deployments/base/v1.13.0-bytecode-manifest.json \
  pnpm -C frontend exec tsx scripts/ops/verify-bytecode-store-seeded.ts
```

## Retry guidance (Phase 1 partials)

If Phase 1 previously partially deployed for the same creator+version tuple:

1. Hard-refresh app/runtime.
2. Use a fresh deployment version namespace (`v1.13.0` or `v1.13.0-*`).
3. Re-run deploy with module/store alignment checks passing.
