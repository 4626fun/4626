## Learned Workspace Facts

- **Robinhood Chain remote ShareOFT expansion (4663 / EID 30416):** Base stays the vault-accounting hub — V1 is remote `CreatorShareOFT` only (`isHub=false`, `hubEid=30184`), no CreatorOVault/gauge/strategies on Robinhood; uses non-common LZ EndpointV2 `0x6F475642a6e85809B1c36Fa62763669b1b48DD5B` (needs `OFTBootstrapRegistry` v2 CREATE2 salt); Base↔Robinhood shared DVNs are LayerZero Labs, Nethermind, Horizen, BitGo, and Canary at 3-of-5 — do not reuse Base↔Solana 6-of-9 DVNs.

- `GET /api/waitlist/stats` serves live waitlist count data for urgency display (`signedUpCount` + up to four recent-member `avatars` from `fetchRecentMemberAvatars` in `_stats.ts`); waitlist capacity uses configurable 100-slot tiers with dynamic "Only X spots remaining!" messaging. **`getWaitlistMemberCount()` in `waitlistLeaderboard.ts` is the SSoT** — counts verified-email profiles excluding merged tombstones (`merged_into_profile_id IS NULL`); both `/api/waitlist/stats` and leaderboard `totalCount` must use it so counts stay aligned. `WaitlistFlow` polls stats every **30s** and refetches immediately after a successful join.

- **Zora profile lookup for 4626 accounts** uses shared `zoraProfileIdentifier` helpers (server `frontend/server/_lib/zora/zoraProfileIdentifier.ts`, client mirror `frontend/src/lib/zora/zoraProfileIdentifier.ts`) with seed priority: handle → Zora cross-app → **canonical CSW (`profiles.csw_address`)** → external EOA → primary wallet → embedded EOA (embedded skipped when CSW is known). Account-scoped flows (`walletSync`, `accountsIdentity`, waitlist bootstrap/preprovision, `useAccountZoraProfile`, deploy/agent register) must not query the Privy embedded EOA when CSW exists; public `GET /api/zora/profile?identifier=` remains a pass-through for explore/chat.

- Canonical CSW owner-install sponsorship accepts `addOwnerAddress` self-calls for the authenticated Privy embedded EOA without requiring deploy-session signer state; keep deploy-session checks scoped to deploy-session automation paths.

- **`resolveWaitlistConnectTrack`** (`waitlistFlowState.ts`) splits waitlist connect/messaging into `base-app-direct` | `zora-owner-install` | `not-ready`. Base App track uses `prepareWaitlistMessagingWallet` → Coinbase connector → canonical CSW → XMTP in one CTA; Zora track stays read-only Zora link → owner install → embedded-EOA messaging. Population (a) can join the waitlist by email only; group chat can unlock via optional Zora/Base App CSW **or** auto-provisioned Privy parent CSW (`WaitlistWalletProvision` / `useEnsurePrivySmartWallet`) plus browser owner install (`WaitlistPrivyWebOwnerInstall` / `usePrivyCswWebOwnerInstall`) — `not-ready` copy must not say "Enable 4626 signing" when no CSW exists yet.

- `/api/onboarding/bootstrap` and `/api/accounts/me` both expose `executionTrack` and `privyEmbeddedEoaIsOwnerOfCanonicalCsw` as the source of truth for execution-track decisions; clients must read these fields rather than recompute routing from wallet state. Server profile resolution for both endpoints must use `listProfileIdsForPrivyUser` (alias-first), not a direct `profiles.privy_user_id = ?` lookup — merged/alias Privy users otherwise miss canonical CSW rows and swap gates falsely show execution-setup-required. Account-setup surfaces (`useAccountSetupController`, `/add`) must merge both via `mergeAccountMeWithBootstrap` — reading `/api/accounts/me` alone can miss canonical CSW already on the profile. **These two endpoints keep coming up as "aren't these duplicates, can we merge them?"** — they're not: `/accounts/me` is a DB-only identity/points read, `/onboarding/bootstrap` resolves execution-track signals via a heavier, separately-cached (30s TTL) canonical-CSW on-chain owner check; merging the handlers server-side wouldn't reduce any actual work and would blur that wallet-invariant separation. `useAccountMe.ts`'s `fetchAccountMe` fetches both **concurrently via `Promise.all`** (split into a standalone `fetchAccountMePayload` helper) rather than sequentially, since bootstrap never depends on the `/me` response — that's the real, safe optimization here, not a backend merge.

- **Waitlist bootstrap auto-adopts wallet-bound Privy collisions** when the active session's wallets match the canonical profile (`runWithWaitlistWalletCollisionAdoption` in `emailCollisionAdoption.ts`): if `WALLET_BOUND_TO_CANONICAL_EMAIL_PROFILE` fires but connected CSW/embedded EOA owns the target row, seed `privy_user_aliases` and retry instead of looping "Use existing account" — distinct from email-collision sign-out recovery.

- **Waitlist returning wallet sign-in uses dual Privy modes on `/waitlist`.** Default `PrivyClientProvider` runs `mode="waitlist-email-only"` (no external wallet connectors during email OTP — Coinbase Wallet SDK and WalletConnect must stay off that path or extension races destabilize OTP). Clicking **Sign in with linked wallet** **key-remounts** the provider (`key=wallet-${attempt}`, not in-place mode mutation) to `waitlist-returning-wallet` + `ethereum-only`, mounts `WaitlistReturningWalletSignInRunner`, and sets `showWalletLoginFirst`. Returning-wallet connectors are **WalletConnect + EIP-6963 detected wallets only** (`WAITLIST_RETURNING_WALLET_LOGIN_LIST`: `detected_ethereum_wallets`, `wallet_connect`) — **Coinbase Wallet SDK is excluded** on this path to avoid localhost `window.ethereum` fights and failed COOP HEAD probes. Both waitlist modes **omit embedded-wallet `createOnLogin`** (localhost/iframe safety), but email-join must still provision an embedded EOA before session mint via best-effort `ensureEmbeddedWallet()` in `establishWaitlistSessionAfterPrivyAuth` (non-fatal if create fails; returning-wallet path stays external-EOA only and may omit the ensure callback). **Do not remount into `waitlist-wallet-joined` immediately after email OTP** — that remount plus loopback `clientId` churn can restore a different Privy session while the 4626 cookie stays on the email-join user, so later wallet SIWE / `/api/accounts/link` attaches Base/CSW to the wrong `privyUserId`; defer wallet-joined remount until explicit wallet-connect intent. **Joined waitlist UI requires both** the HttpOnly `cv_auth_session` cookie **and** `privy.authenticated` (`resolveWaitlistJoinedSessionAddress` in `resolveWaitlistJoinedSession.ts`); an orphan cookie without Privy shows the signed-out email view (0 pts, empty linked identities). Debounced orphan cleanup via `shouldClearOrphanWaitlistServerSession`; gate `useAccountMe` until actually joined. After wallet sign-in, call `invalidateAccountMeCache()`; bootstrap must attach wallet-only Privy users to existing `profiles` / linked-wallet rows when Privy omits verified email.

- **Waitlist Privy session bridge (`waitlistPrivySession.ts`).** After auth, treat the address returned from `bridgePrivySession` → `/api/auth/privy` as session truth — do not require an immediate `/api/auth/me` confirm (rate-limit backoff and stale Bearer shadowing cause false "session still syncing"). Call `ensureEmbeddedWallet` (when provided) after the Privy token is confirmed and **before** `bridgePrivySession` so zero-wallet brand-new signups do not 400. **Do not call full Privy logout before wallet reconnect when a live access token exists** — reuse the token and bridge; if `authenticated` but tokenless, clear the 4626 server cookie only (`shouldLogout: false`). Skip a second `login()` when already authenticated; poll for the access token, then bridge. Rollback after failed bridge should avoid unnecessary Privy SDK logout (400 noise on `sessions/logout`).

- **Privy server wallet create/provision must use the `wallets` array API** (`wallets: [{ chainType: 'ethereum', policyIds: [] }]`) — deprecated wallet-count parameters are rejected and surface as `auth.privy.io` passwordless/authenticate **422**, leaving waitlist join stuck with `privyAuthenticated: true` but no 4626 session.

- **4626 admin waitlist (`/admin/waitlist`, `/api/admin/waitlist/list`) is not the Privy dashboard user list.** Admin rows come from Supabase `profiles` / waitlist bootstrap (`POST /api/waitlist/bootstrap`); Privy dashboard users can exist before bootstrap completes. Users in Privy but missing from admin usually mean bootstrap never finished, bootstrap failed (check Vercel `waitlist/bootstrap` logs), or admin is pointed at a non-production DB — not a Privy sync bug.

- `/accounts` redirects to `/waitlist`; the advanced account-setup controls live in `WaitlistAdvancedSection` mounted inside the waitlist page (no separate `/accounts` UI).

- `referral_passthrough` is a first-class `waitlist_points` source written by `recordReferralPassthrough` in `frontend/server/_lib/onboarding/waitlistPoints.ts`; it credits referrers with 50% of every point the referee earns, and every scoring query (`waitlistLeaderboard.ts`, `waitlist/_position.ts`, `waitlist/_referrer.ts`, `accountsIdentity.ts`) must include this source. Invariants, all enforced in code:

- AMOE ↔ waitlist points bridge: `awardAmoeCheckinPoints` in `frontend/server/_lib/lottery/amoeWaitlistPoints.ts` is called from `claimDailyTwitterCheckin` in `frontend/server/_lib/lottery/lotteryAmoe.ts`; AMOE entry submissions no longer award waitlist points.

- **AMOE off-chain credit constants are not interchangeable.** `AMOE_CREDITS_PER_ENTRY` (100 in `lotteryAmoe.ts`) is credits burned per lottery entry submission; `AMOE_DAILY_TWITTER_CREDIT` / `AMOE_DAILY_XMTP_CREDIT` are daily earn amounts (currently **1 credit/day** each after reverting a temporary 100/day promo); frontend `AMOE_MIN_POINTS` (100 in `AmoeEntryCard.tsx`) is the minimum variable burn for ZK submit — distinct from daily check-in credits. Daily check-in waitlist bridge stays **6 points** via `amoe_checkin`, not tied to AMOE credit amounts.

- **Twitter credentials split (`frontend/server/twitter/twitterEnv.ts`).** Protocol lane uses `X_*` env vars with fallback to `TWITTER_*` / `HERMIT_TWITTER_*`; `X_BEARER_TOKEN` for server tweet verification (AMOE daily X check-in); OAuth 1.0a keys for protocol posting (`X_*`) or bot/Hermit posting (`HERMIT_TWITTER_*` when `HERMIT_TWITTER_STRICT`); Privy dashboard OAuth 2.0 is for user account **linking** and is separate from AMOE verify + bot lanes.

- **Privy OAuth provider linking (`frontend/src/lib/privy/providerLink.ts`).** Shared init/sync/unlink for waitlist + account setup: `linkPrivyProvider`, `syncAccountsProviderLink` (retries `No linked value found for provider`), `linkAndSyncPrivyProvider`; token reads via `accessToken.ts`; safe hook wrappers in `safeHooks.ts`. Deleted parallel waitlist-only `useWaitlistTwitterLink.ts` / `waitlistPrivyToken.ts`.

- **Waitlist Twitter/X OAuth linking.** Sanitize redirect URL via `sanitizeCrossAppRedirectUrlForAuth()` before `linkTwitter*`; in `waitlist-email-only` mode set `customOAuthRedirectUrl` to `/waitlist` and include `twitter` in Privy `loginMethods`; on recoverable generic `Authentication failed`, fall back to `login({ loginMethods: ['twitter'] })` then `/api/accounts/link` sync. Privy **Redirect URLs** (not just Allowed Origins) must list exact localhost paths like `http://localhost:5174/waitlist`; X Developer Portal callbacks must include `https://auth.privy.io/api/v1/oauth/callback` and `https://privy.4626.fun/api/v1/oauth/callback`.

- **Waitlist X engagement (post link).** Sequential one-at-a-time quest steps: **Follow → Repost → Comment** (Option A — **Like dropped**; not verifiable on app-only bearer). Default is **follow-only** until server env `WAITLIST_X_ENGAGEMENT_TWEET_URL` or `WAITLIST_X_ENGAGEMENT_TWEET_ID` is set (`waitlistTwitterEngagementConfig.ts`) — then repost + comment unlock without code changes (12 XP total; follow-only = 4 XP). UI reads `steps`, `campaignTweetId`, and `campaignTweetUrl` from `GET /api/waitlist/x-engagement`.

- **Waitlist X engagement verification.** **Follow auto-awards** via Account Activity webhook (`follow_events` when someone follows `@4626fun`) — no "Verify on X" click required; UI poll (~3s) reads **DB/points only**, not X. **Repost + comment** require on-demand **Verify on X** (`POST` + `verifyEngagement.ts` + `X_BEARER_TOKEN` timeline scan). Production verification uses **bearer + webhook + Privy-linked identity** — **not** Cursor X MCP (`xapi`/`x-docs`), which is dev tooling only.

- **AMOE `points` ledger identity (`amoeProfileResolve.ts`).** Twitter daily awards use `verified_privy_only`; waitlist `amoe_checkin` bridge uses `privy_linked`; anonymous lottery ledger may create synthetic `amoe-*@wallet.4626.fun` under `lottery_ledger` policy.

- **Public points are one weighted total everywhere.** `readWaitlistPointsBreakdown` in `waitlistScoring.ts` is the SSoT for tray/waitlist tiers (`score.points`), `/api/waitlist/position` `points.total`, `/api/v1/lottery/amoe/credits`, and lottery spend gates — do not reintroduce a second `lotteryCredits` / `amoeCredits` / `points_amoe_eligible_balance` balance for user-facing totals. AMOE ledger sources (`amoe_entry_spend`, `amoe_twitter_daily`, `amoe_xmtp_daily`, `amoe_entry_refund`) contribute **0** to that weighted sum; only `amoe_checkin` counts among AMOE-family sources on public surfaces.

- **Account tray points are Privy-only and fail closed.** `GET /api/accounts/me/points` must resolve via `buildAccountTrayPointsForPrivyUser` in `frontend/server/_lib/onboarding/accountTrayPoints.ts` (alias-aware `resolvePrimaryProfileIdForPrivyUser` → `profiles.id`); do not reintroduce wallet-based tray rank/history. Requires `X-Privy-Token`; client uses `fetchAccountTrayPoints` (throws `AccountTrayPointsAuthError` without token). Rank/`totalCount` are withheld unless `leaderboardEligible` (verified non-synthetic email, non-tombstone). `/api/waitlist/points-activity` delegates to the same builder for history-only callers. Integrity guards: `account_tray_points_profile_mismatch`, `account_tray_points_breakdown_mismatch`, `account_tray_points_tier_mismatch`. Tray UI uses one unified points total everywhere (not separate waitlist/leaderboard/lottery balances in copy), tab order **Overview → History → Leaderboard**, edge-to-edge activity/history panels without nested bordered cards, and Zora username on leaderboard rows when available (else Basename/CSW).

- Waitlist wallet-readiness follows **population tracks** without Privy Smart Wallet auto-provision: Zora population (c) uses parent CSW + Privy embedded-owner (`legacy-owner-install`); Base App population (b) with `canonical_source === 'base_account'` uses additive `base-app-direct` (parent CSW identity + Base App connector signing when that track applies). Users link an existing Coinbase/Base CSW explicitly — do **not** recreate `WaitlistWalletProvision` / `useEnsurePrivySmartWallet`. Gate embedded-EOA presence on `useEnsurePrivyEmbeddedWallet().embeddedEoaAddress` (or server-owned ensure), not `privy.user.wallet.address`. Zora `/swap` setup CTAs still deep-link to `/waitlist?setup=owner-install`. Do not revive `ownerInstallMapping.ts` wholesale.

- **`resolveWaitlistStep` must not regress verified users to email auth.** When email is verified but signing is incomplete, route to the `done` setup workspace (not `auth`). **`shouldAutoBootstrapWaitlistSession` stays false** — bootstrap runs only after explicit Continue, not on Privy auto-restore. When Privy marks authenticated but `login()` never resolves after email OTP, resume bootstrap from an auth-pending flag instead of leaving the full-screen "Loading…" overlay stuck.

- **HttpOnly `cv_auth_session` ≠ Privy session.** Users can have a 4626 session cookie while `privyAuthenticated` is false; canonical `/swap` then shows **Privy sign-in required**. On `/waitlist`, that orphan state must not render the joined view — see `resolveWaitlistJoinedSession.ts`. Restore Privy with email OTP (`signIn({ method: 'privy' })` / waitlist email), not Base-only wallet connect. In `useSiweAuth`, `preferBaseAccountWallet: true` must still call `setActiveWallet` after `connectWallet` and fall through to `login()` when no Privy access token is present — connecting Base alone does not load the embedded signer.

- **Waitlist/chat/Zora session repair shares `frontend/src/lib/auth/sessionRepair.ts`.** Use `attemptSessionRepair` + `createStaleSessionProbe` (double-probe; true-stale only after `>= 2` misses with no live `cv_auth_session`) — a single null `getAccessToken()` after OTP is transient, not hard sign-out. XMTP mounts repair via `useXmtpSessionRepair`/`ChatProviderWithSessionRepair`: one bounded repair + single `connect('user')` retry before embedded-signer expired copy. `ChatBar` Connect uses `connectBusy` with ~15s safety timer. Zora cross-app timeout/auth/collision failures degrade to read-only `resolveZoraReadOnlySignals` (`/api/zora/resolve`); `isWalletProviderCollisionError` must not count as stale session.

- **`useEnsurePrivyEmbeddedWallet` lives in `@/lib/privy/embeddedWallet`**, not under `@/hooks/`.

- **Privy uses the custom auth domain `privy.4626.fun` with per-environment dashboard clients.** That domain must be present in the app CSP `frame-ancestors`/connect rules and in the Privy app's allowed domains/origins alongside `4626.fun`, `app.4626.fun`, localhost dev ports, and `web.telegram.org`. **Production CSP `connect-src` in `frontend/vercel.json` must include `https://privy.4626.fun` and `https://privy.app.4626.fun`** (not just `frame-src`/`child-src`) — the SDK's session-refresh fetches hit `https://privy.4626.fun/api/v1/sessions`, and blocking them leaves Privy init permanently stuck (loading overlay `held by: privy-init`); regression test in `alfaclubVercelWiring.test.ts` pins both domains in `connect-src`. Privy clients are environment-scoped (Local Dev / Production Web / Production Mobile) — a stale or mismatched `VITE_PRIVY_CLIENT_ID` in a running dev server surfaces as `Invalid app client ID` / "Something went wrong"; restart the dev server after `.env` Privy changes before debugging deeper. Cookies are enabled on the `4626.fun` base domain so sessions survive the marketing ↔ app host split.

- **AlfaClub product shell is `alfaclub.4626.fun`** with canonical `/rooms`, `/safety`, and `/pools`, and the intended home for the full **`/arena`** trading surface. Legacy `/alfaclub/*` URLs on marketing/app hosts hard-redirect there; LP directory browse is public and LP writes stay session + wallet gated. **`4626.fun` and `app.4626.fun` otherwise stay normal** (waitlist/swap/deploy/explore unchanged) — AlfaClub is a third host, not a second account system; shared `.4626.fun` session cookie; chat API proxy stays on `relay.4626.fun`. Privy dashboard **Allowed Origins** and **OAuth Redirect URLs** must include `https://alfaclub.4626.fun` (and path-specific redirects used for sign-in return) — missing allowlists send users through waitlist and block liquidity management.

- **Privy on localhost has two session lanes.** **`PrivyClientProvider` on loopback waitlist routes omits `clientId` and `apiUrl`** (`isLocalDevPrivyApiBypass()` in `client.tsx`) so wallet/email sessions use app-id **localStorage**, not `privy.4626.fun` server-cookie mode — this is intentional for waitlist OTP and returning-wallet reconnect. When the SDK drifts into custom-domain server-cookie mode on localhost, pin `apiUrl` to `https://auth.privy.io` and no-op `POST /api/v1/sessions` bodies with `refresh_token: "deprecated"` (returns `{ session_update_action: "ignore" }`) instead of letting them 400. Marketing `/waitlist` must wrap `AppQueryProvider` — joined views render `WaitlistWelcomeGreeting`, which uses React Query via `useChatIdentity`. Non-waitlist localhost routes (deploy/swap) may still use the custom auth domain when `VITE_PRIVY_CLIENT_ID_ON_LOOPBACK=1`; there `loopbackSessionMarkerShim` re-asserts the `privy-session` marker every 2s because server cookies are third-party on loopback. Localhost sessions do **not** survive a hard page reload, the embedded-signer iframe session lives ~1 hour, and Zora cross-app OAuth is structurally flaky on localhost — documented limitations, not bugs. **Deploy-dry-run on `localhost:5174` must enable the Privy App Client lane** (`VITE_PRIVY_CLIENT_ID_ENABLED=1`, `VITE_PRIVY_CLIENT_ID_ON_LOOPBACK=1` in `frontend/.env.deploy-dry-run.local` and defaults in `scripts/dev-deploy-dry-run.sh`); without it session bootstrap hits `POST https://privy.4626.fun/api/v1/sessions` → **400** and the `privy-init` bootstrap overlay never clears (looks like a blank page) — stale/corrupt Privy cookies often cause the same 400; clear site data for `localhost` and `privy.4626.fun`. For waitlist debugging, multiple wallet extensions cause `window.ethereum` collision noise, WalletConnect multi-init, and Privy init hangs — prefer a **private/incognito window with one extension** (or none for email-only OTP). **`/deploy/vault` redirects unsigned users to `/waitlist`** — that is expected gating, not a dead Vite route. **"Missing auth token" from inside the Privy embedded-wallet iframe** (raw digest signing, XMTP signers) means a stale/expired iframe session: page-side token refresh cannot fix it — only a real Privy logout + fresh email-OTP login re-seeds the iframe. `/swap` surfaces a "Sign in again to fix signing" recovery CTA for this, and refresh checks must decode the JWT `exp` (a truthy-but-expired token is a failed refresh, not success).

- **Smart-wallet Permit2 (canonical CSW sells) needs raw digest signing from the embedded EOA.** Privy unified-stack embedded wallets with `owner_id` (user key quorum) must sign `secp256k1_sign` via **`privyAuthorizedWalletRpc.ts`** with both `Authorization: Bearer <access token>` and **`privy-authorization-signature`** from Privy `useAuthorizationSignature` — access-token refresh alone does not fix **401** on `privy.4626.fun/api/v1/wallets/.../rpc`; the signed payload URL must be the **full RPC URL**, not a path-only string. Wire through `useSwapEmbeddedEoa` → `signRawEcdsaDigest` (optional `signSecp256k1Digest` callback). Server-side Wallet API automation uses a separate **`PRIVY_WALLET_AUTHORIZATION_KEY`** quorum lane (`privyWalletApi.ts`), not the browser user authorization key. `signRawEcdsaDigest` still tries `eth_sign` param shapes and treats disconnected-session / iframe stale-token errors as refreshable; `useSwapEmbeddedEoa` must not treat `signMessage`-only wallets as sign-ready for canonical Permit2.

- **Waitlist Airtable sync is an ops mirror, not account truth.** `/api/waitlist/airtable-sync` is cron-secret protected and writes server-side Airtable rows from Supabase; Airtable may carry review/outreach fields, but it must not rewrite points, referral ownership, wallet readiness, CSW addresses, Privy IDs, or Telegram linkage. Keep merge keys stable: referrals include `id` from `referral_conversion_id`, onboarding upserts by `signup_id` with a legacy `canonical_wallet` / `profile:` backfill before the `signup_id` upsert. `Personalized Onboarding Email` in the applicants table is an Airtable-owned `aiText` field, not API-writable; use an Airtable AI prompt there, or add a separate writable long-text field if server-generated drafts are needed.

- Accounts page is expected to list all owners of the canonical Zora CSW (`profiles.csw_address`) with an optional revoke control; any canonical-CSW automation must reuse the existing deploy-session Privy embedded-EOA signer pattern rather than silently calling `addOwnerAddress` to add new owners — the "why is the deploy flow trying to add a new owner to my CSW?" complaint is a recurring regression signal.

- **`INSERT INTO profiles` must be preceded by a canonical-collision check** whenever the call site has a Privy user id in scope. Use `assertNoWalletPrivyCollision({ db, privyUserId, privyUser })` (or `{ ..., evmAddresses }` when you already have a classified address list). Current guard sites: `api/_handlers/waitlist/_bootstrap.ts` (runs before upsert), `wallet/walletSync.ts:insertOrUpdateProfile` (runs before new-row INSERT only). Skipping this guard re-opens the split-identity bug where a wallet-login Privy user creates a fragment while a canonical email-verified profile already owns the same EOA.
