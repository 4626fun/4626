- Vault-deploy product invariants: a creator must deposit between **50,000,000 and 100,000,000** of their Creator Coin as principal before deploying a vault (50M stays the floor per the 5%-of-supply invariant; the exact-50M pin was relaxed June 2026 by hot-swapping `DeploymentBatcherPhase2Module` to `0xdDbD468271BffF84De09AAc3C43B582e2dBEDC5E` via protocol-treasury-Safe `setPhase2Module` — the pre-v1.14.1 batcher shell `0xa99058…0651` stayed in place (superseded June 2026 by v1.14.1 batcher `0x660B251F2feB28f61A8e23e65C66F9b917Ee61c1`)). Frontend honors `?minFirstDepositTokens=…` / `VITE_MIN_FIRST_DEPOSIT_TOKENS`, clamped to the 50M–100M range; default remains 50M. Future module rotations: `frontend/scripts/ops/execute-set-phase2-module-safe.ts` plus the fork rehearsal pattern in `test/fork/DeploymentBatcherPhase2ModuleHotSwap.fork.t.sol` (validate live shell + new module on a mainnet fork before the Safe swap). Initial CCA seeding is 99% creatorCoin / 1% USDC (not a balanced pair); each wallet is capped to one deploy per `deployment version` (current copy: "v1.2.3x"), enforced on the Deploy page.

- **Never call bare `isOwnerAddress` on counterfactual smart wallets.** Guard with `readIsOwnerAddressIfDeployed` (`frontend/src/lib/wallet/cswOwnerRead.ts`) / `getBytecode` first; undeployed wallets return `unknown`, not a viem `"returned no data"` error.

- **Greenfield vault deploy requires paid `vault_full_deploy` ($499 USDC, all-or-nothing).** `docs/operations/creator-strategy-features.md` is the canonical spec. Public catalog sells one bundle that expands to Charm (`charm_active_lp`) + Ajna (`ajna_sleeve`) at **45%/45%** Phase 3 weights, `solana_ovault_mesh` (Phase 2b Pipe A finalize bridge, not Phase 3 TVL), and `solana_meteora_alpha_vault` (Meteora entitlement, operator-provisioned post-deploy). **À-la-carte purchases** of those four keys return **HTTP 410** — activate `vault_full_deploy` at `/creator/strategy/features`. AKITA operator comp rows still resolve. **Three payment paths**, all landing in the same `creator_strategy_features` row with a `payment_source` discriminator: (1) `usdc_base` — creator sends a plain USDC `transfer` + POSTs tx hash to `/api/creator/strategy/activate`; verifier matches `Transfer(from=session,to=treasury,value>=effective)` log regardless of tx shape. (2) `x402_base` — creator POSTs `/api/creator/strategy/x402-activate` without a tx hash; server replies HTTP 402 with payment requirements; client signs EIP-3009 `TransferWithAuthorization`, base64s it into `X-PAYMENT` header, resubmits; server relayer (`X402_RELAYER_PRIVATE_KEY` or fallback `PRIVATE_KEY`) broadcasts `usdc.transferWithAuthorization(...)` and pays Base gas — single round trip, gasless for creator; `UNIQUE (payment_from, x402_authorization_nonce)` prevents replay. (3) `stripe` — creator POSTs `/api/creator/strategy/stripe/checkout`, server creates a Stripe Checkout Session (USDC price → USD cents via `floor(priceUsdc / 10_000)`), client redirects, Stripe webhook `checkout.session.completed` hits `/api/creator/strategy/stripe/webhook` which finalizes the row; Stripe fees apply (~$14.77 on a $499 bundle sale). **Discounts are supported operator-side** via `creator_strategy_price_overrides`: insert a row scoped to `creator_token` (per-vault) or `wallet_address` (per-buyer) with a `price_usdc_override` (and optional `expires_at`). `findActivePriceOverride` prefers creator-scoped match first then wallet-scoped; `applyPriceOverride` clamps effective price to `min(override, catalog)` so a malformed override can never raise prices. All three payment paths honour overrides: USDC clamps `minAmount`, x402 clamps `max_amount_required` in the 402 response, Stripe converts the discounted USDC into cents. **`vault_full_deploy` (or legacy Charm+Ajna entitlements) is required** — `DeploymentBatcher.deployPhase3Strategies` reverts with `InvalidWeight` when `charm+ajna == 0` (Phase 3 `solanaWeightBps` is always 0; Solana share seeding is Pipe A at finalizePhase2), `computeStrategyWeights` returns `{ok:false, reason:'no_paid_strategies'}`, and `/api/creator/strategy/list` returns `deployPlan.deployable = false` with `blockedReason = 'no_paid_strategies'`. **Weight scaling:** with the bundle (or both legacy keys), **4_500 bps Charm + 4_500 bps Ajna + 1_000 idle**; legacy single-strategy comps still get 9_000 bps on the paid leg only. Payment: client sends USDC `transfer` on Base to `protocolTreasury` (overridable via `CREATOR_STRATEGY_FEATURE_USDC_TREASURY`), POSTs `{creatorToken, featureKey, paymentTxHash}` to `/api/creator/strategy/activate`. `verifyUsdcPayment` is authoritative on the decoded `Transfer(from=session, to=treasury, value>=price)` log — tx shape (multicall, UserOp, router) doesn't matter, only the log. Deploy-side: `resolveCreatorStrategyPlan(db, creatorToken)` in `frontend/server/_lib/creatorStrategy/resolveWeights.ts` returns a tagged `{ok:true,plan}` or `{ok:false,reason:'no_paid_strategies',...}`. The patched `DeploymentBatcher.deployPhase3Strategies` skips the factory call + strategy deploy + `addStrategy` for any strategy with `weightBps == 0`; `StrategyCodeIds` for skipped strategies may be `bytes32(0)`. Phase 3 deploys Charm + Ajna vault strategies only (`solanaWeightBps` always 0). Uniswap V3 CREATOR/USDC pool creation stays unconditional so future Charm activation has a pool ready, so single-strategy deploys must still pass `initialSqrtPriceX96 > 0` when the pool doesn't pre-exist. DB is `creator_strategy_features` with `UNIQUE (creator_token, feature_key) WHERE status IN ('pending','active')` and `UNIQUE (payment_tx_hash)`. `pending` == "paid but provisioner hasn't run yet"; the resolver counts both `pending` and `active` as paid so creators can deploy immediately after their USDC clears. **Post-deploy strategy addition (operator / legacy partial vaults only):** public API cannot buy individual strategies; operator runs `pnpm -C frontend exec tsx scripts/activate-strategy-post-deploy.ts --creator 0x… --feature <key>` for Safe calldata when a legacy vault deployed with only one strategy. All three payment handlers (`_activate.ts`, `_x402-activate.ts`, `stripe/_webhook.ts`) call `dispatchProvisioning` in `server/_lib/creatorStrategy/provisioner.ts` after row insertion — for v1 that's an enqueue-only stub that logs intent + returns an operator-targeted note; any failure is non-fatal (the `pending` row is the source of truth, operator polls). **Creator-facing UI is live at `/creator/strategy/features`** ([`frontend/src/pages/CreatorStrategyFeatures.tsx`](frontend/src/pages/CreatorStrategyFeatures.tsx)) — reads `/api/creator/strategy/list`; deploy strategies stay full cards with USDC/x402/Stripe payment, while vanity tiers are grouped into two collapsed optional sections via `frontend/src/lib/creatorStrategy/featuresPageLayout.ts` (vault prefix + share suffix tables). Unpaid deploys show an amber **activate `vault_full_deploy`** blocker. Operator comps: `pnpm -C frontend exec tsx scripts/grant-creator-strategy-comp.ts --creator=0x… --all-deploy-gating --execute --confirm=GRANT-STRATEGY-COMP` inserts `$0` `creator_strategy_price_overrides` and optional pending activation rows. **Superseded v1.14.1 greenfield deploy infra:** the then-active `DeploymentBatcher` was `0x660B251F2feB28f61A8e23e65C66F9b917Ee61c1`, with Phase1Module `0x0fac3F8040879eF1ca6cc4572cc27f0908a8f266`, chunked bytecode store `0xb3712E84F123e7C5390913E30FC6BBD5AEd2a314`, CREATE2 deployer `0x2fA570Cb17925Da86b303D4651f06b83057a10c4`, registry `0xDD7B106a15540bA2F59464590222bF47D8C9394E`, and Solana adapter `0x8e99bb0270bbdf2d64ff6854509CD2410A28fBae`. Preserve `deployments/base/v1.14.1-bytecode-manifest.json` as historical evidence; current v1.19.1 pointers are below. Paymaster-side `gateRequestedStrategyWeights` IS now wired into `api/_handlers/paymaster/_paymaster.ts`: Phase 3 UserOps are rejected with `paywall_weight_gate:<reason>` or `paywall_db_not_configured` before sponsorship if requested weights don't match the resolved paid plan; skipped strategies' codeId/keeper args may be zero. AKITA stays pinned to the v1.8.3 batcher at `0xcDbEeB76…C4F` (grandfathered, unaffected). **Still pending:** (a) Stripe end-to-end test against a real Stripe signature (signature verification path is confirmed; real payload handling depends on body-parser behavior), (b) x402 in-dapp wallet-signing helper (currently the UI surfaces raw 402 requirements for manual EIP-3009 signing), (c) automated Safe broadcast from the activation script (today the script prints calldata; operator submits via Safe UI). Adding a new feature = catalog entry + union member + runbook subsection in the doc; no migration.

- **Vault deploy pricing is flat-rate and USDC-denominated for now.** Per-strategy purchase pricing is removed; an AKITA-denominated deploy payment (Virtuals-style, paying in `$AKITA` `0x5b674196812451b7cec024fe9d22d2c0b172fa75`) is an explicitly deferred future phase — product decided to keep USDC pricing at launch and revisit AKITA value-capture via post-settlement routing later, partly because AKITA's USD price is too volatile/low to anchor pricing today. **The paid gate is surfaced on `deploy/vault` itself, before the flow:** `DeployVault.tsx` queries `/api/creator/strategy/list?creator=…`, blocks `canDeploy` unless `vault_full_deploy` is active, shows a "USDC deploy feature active" readiness row, and renders a blocked card linking to `/creator/strategy/features?creator=…` — do not rely on the strategy-features page alone to communicate the paywall.

- **Charm and Ajna coordinate only through the parent vault idle CREATOR buffer, not direct strategy-to-strategy transfers.** `deployToStrategies()` / `tend()` split idle above `minimumTotalIdle` into weighted `deposit()` calls; user withdrawals pull strategies back via `_withdrawFromStrategies()`. `updateStrategyWeight()` changes target bps only — it does not auto-move TVL, and there is no vault `deallocate()`. Post-deploy weight shifts (e.g. Charm-only → 45/45) converge via KPR `vault-strategy-reallocator` calling `rebalanceStrategies()` (up to `VAULT_STRATEGY_REALLOC_MAX_PASSES` per tick, default 4) plus keeper_jobs `rebalance` workflow when enabled. **`CreatorCharmStrategy` may optionally borrow CREATOR from Ajna on withdraw shortfalls and repay on deposit** — that backstop is separate from the **`ajna_sleeve`** lending lane.

- **Active chunked bytecode store seeding must include frontend deploy bytecode IDs as well as Forge artifacts.** The deploy page/paymaster use `frontend/src/deploy/bytecode.generated.ts` `DEPLOY_BYTECODE` code IDs; if the store is seeded only from current Forge artifacts, preflight can report missing bytecodes for contracts such as `OFTBootstrapRegistry`, `CreatorShareOFT`, `CreatorPayoutRouter`, `CreatorOVaultWrapper`, `CreatorGaugeController`, `CCALaunchArm`, `CreatorOracle`, `CreatorVaultShareBurnStream`, `AjnaERC4626Vault`, and `ERC4626StrategyAdapter` even when similar artifact bytecode is present. `OFTBootstrapRegistry` must implement `getEidForChainId` because `CreatorShareOFT` resolves its LayerZero EID in the constructor.

- **UniversalCreate2DeployerFromStore is ACL-gated, and creator CSWs should not be individually authorized.** Direct deploy calls are allowed only from its owner or `authorizedDeployers`; creator-facing Base App/canonical-CSW deploy flows must route stored-bytecode CREATE2 through an authorized `DeploymentBatcher`, while direct deployer authorization stays limited to protocol/operator deploy surfaces. If deploy preflight reports creator-CSW CREATE2 authorization blockers, rotate to or configure a deploy-capable batcher rather than repeatedly authorizing each creator wallet. **The superseded v1.14.1 Phase1Module used CREATE2 deployer `0x2fA570Cb17925Da86b303D4651f06b83057a10c4`** paired with chunked bytecode store `0xb3712E84F123e7C5390913E30FC6BBD5AEd2a314` (the still older unchunked pair was deployer `0x4760216…` → store `0x8B51…`). Keep `contracts.defaults.ts`, Vercel `UNIVERSAL_CREATE2_FROM_STORE` / `VITE_UNIVERSAL_CREATE2_DEPLOYER`, and `.env.deploy-dry-run.local` on the same canonical epoch; `DeployVault` prefers `create2Deployer()` from the wired Phase1Module before falling back to defaults. **Phase1Module `create2Deployer.store()` must equal wired `bytecodeStore`** — CREATE2 reads the deployer immutable store, not the batcher getter; mismatch causes missing-bytecode preflight (`resolveAlignedPhase1DeployDeps`).

- **Phase 3 CREATE2 runs from `phase3Helper` (external call), not batcher delegatecall.** Phase 1/2 delegatecall keeps `msg.sender` as the batcher shell; Phase 3 external-calls the helper so CREATE2 `msg.sender` is the helper address — it must be on `authorizedDeployers` or deploy reverts `NotAuthorizedDeployer()` (`0x8164ae93`). After v1.12.0 helper rotation run `authorize-phase3-helper-create2.ts`; dry-run forks auto-prep via `ensurePhase3HelperCreate2AuthorizationOnFork`; live check: `verify-phase3-helper-create2-auth.ts`.

- **Deploy preflight bytecode/config reads may fall back to Base public RPC, but execution must not.** `DeployVault.tsx` uses a read-only `https://mainnet.base.org` fallback when the browser wallet RPC returns empty bytecode for live Base contracts; actual deploy transactions still route through the normal wallet/UserOp path.

- **Greenfield Solana liquidity is LayerZero ShareOFT at finalize.** Phase 3 remains 45% Charm + 45% Ajna with `solanaWeightBps == 0`. The Twin adapter, Solana vault strategies, rebalance action, entry relay, and winner relay were removed; optional Meteora setup uses the distinct per-creator LZ share mint.

- **Charm Alpha Vault deploy sets `rebalanceDelegate` to the creator CSW (`params.owner`), not protocol treasury.** `DeploymentBatcher` Phase 3 keeps `manager: protocolTreasury` for fee/parameter control; only the rebalance trigger address moves to the vault owner CSW.

- **Hermit is the AlfaChat creative/meme lane, distinct from Keepr-critical agent paths.** Keep Hermit flows scoped to creative/meme generation and Pinata/IPFS publishing; do not mix Hermit command behavior into Keepr, deploy, wallet, or other critical automation surfaces.

- **Deploy dry-run local forks are shared and stateful.** `pnpm -C frontend run dev:deploy-dry-run` uses a local Anvil fork and `frontend/.env.deploy-dry-run.local`; set `DEPLOY_DRY_RUN_USE_LOCAL_BATCHER=1` when the run should deploy a fresh local batcher onto the fork instead of using the configured/live batcher. Dry-run code should reset/snapshot the fork, reassert impersonation before calls, skip already-complete deterministic phase core only when all expected contracts exist, and fail partial phase state with reset/new-version guidance instead of surfacing raw `No Signer available` or `DeployFailed()` noise. **Phase 2 finalize dry-run prep:** when unauthorized on the fork, impersonate registry owner and call `setAuthorizedFactory(batcher,true)` via `ensureBatcherRegistryAuthorizationOnFork` (`frontend/server/_lib/deploy/ensureBatcherRegistryAuthorization.ts`); attach Pipe A LZ native fee to finalize calls through `attachFinalizeShareBridgeValueToCalls` (same path as live `_continueCore.ts`) — `value: 0 ETH` on finalize is a dry-run bug, not a successful Pipe A quote. **Phase 3 dry-run prep:** auto-authorize `phase3Helper` on the create2 deployer via `ensurePhase3HelperCreate2AuthorizationOnFork` (same pattern as registry auth); stale forks missing helper auth fail Phase 3 with `NotAuthorizedDeployer()` (`0x8164ae93`).

- **Default vanity misses are best-effort again.** In `resolveDeployVanityPlan`, when planner outcome is `missed_defaults`, default targets (`0x4626` vault prefix / `4626` share suffix) now continue with warning text instead of hard-failing; explicit custom vanity requests still fail closed.

- **DeploymentBatcher constructor changes require a complete root call-site sweep.** When changing `DeploymentBatcher` or `DeploymentBatcherPhase2Module` constructor signatures, audit all root `contracts/`, `script/`, and `test/` call sites before patching fixtures; `.worktrees/**` hits belong to separate worktrees and should not be edited from the root checkout.

- **DeploymentBatcher's large constructor is sensitive to viaIR stack pressure.** Keep zero-address checks interleaved immediately before each state assignment and use state-var reads in helper `new` calls; regrouping constructor param checks can recreate the `Variable value4 is 1 too deep in the stack` Yul failure.
