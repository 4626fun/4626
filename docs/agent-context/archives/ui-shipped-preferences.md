## Learned User Preferences

- For waitlist and account-setup surfaces, stay on the product brand palette (blue primaries with dark charcoal or near-black backgrounds) rather than purple or ad hoc accent colors unless design explicitly calls for something else. Build product UI on shadcn/Radix `@/components/ui/*` plus existing Tailwind brand tokens — use `<Button>` and siblings, not raw `btn-*` classes, CDS, or parallel ad hoc styling lanes.

- Prefer progressive disclosure in multi-step onboarding: emphasize the active step, collapse or quiet completed steps, and avoid duplicate titles or redundant headers on loading screens.

- Keep secondary actions such as Previous Step and Retry visually quieter than primary blue actions.

- When Zora linking is the active context, prefer showing the Zora handle as the human-readable identity label over a truncated wallet address that does not match what the user expects for their canonical smart wallet.

- For waitlist/onboarding UI, prefer cleaner card treatments with minimal framing; remove heavy outer borders when they add visual noise. Avoid nesting every setup step in boxed/bordered card shells — use typography hierarchy, whitespace, and timeline rails instead of stacked nested panels.

- For exported skill/context documentation packs and Notion uploads, prefer comprehensive self-contained writeups that assume the reader does not have direct repository access; preserve source-document detail, section structure, tables, caveats, and action lists unless the user explicitly asks for a condensed edition.

- Waitlist primary CTAs use opt-in `.btn-3d` on `.btn-accent`: a solid colored cap on a darker side ledge with a small neutral drop shadow — no colored glow, bloom, or glossy pill treatment; user explicitly rejected over-glowing buttons in favor of a tactile, pressable look.

- Explore dashboard and hero metrics must present only verified indexed totals — no live Zora read-path blending, synthetic inflation, or implied platform-wide totals during partial backfill; label indexed scope honestly when sync is incomplete.

- For metric/analytics charts on content-detail and vault surfaces, prefer a single multi-series chart with toggleable series (price/liquidity/volume/fees) over separate per-metric charts — render volume as bars, fees as cumulative bars, and liquidity as bars split by the two pool tokens. Charts must fill the full component area without feeling cramped, and axis value labels must sit on the correct axis (Y-axis values along the vertical axis, not rendered as a horizontal row below).

- For nav bars, prefer edge-to-edge layout over centered max-width, text-only links without hover backgrounds, and no visual separators between nav and content.

- Prefer aggressive simplification passes in large folders: identify and remove or archive unnecessary files (including `.ts`/`.tsx`), not just documentation, to reduce complexity.

- During database/storage optimization sweeps, preserve real/raw data — remove only derived or regenerable artifacts (duplicate indexes, matviews, snapshot retention within approved windows, bloat). Data-loss levers such as dropping audit columns or pruning source rows require explicit user approval; default answer is no.

- During broad cleanup/refactor sweeps, prefer sustained autonomous execution with minimal pause-and-confirm loops, and parallelize with subagents to expedite when the sweep spans many files or folders.

- Do not rewrite or redesign the premium token icon renderer — keep the existing deterministic Sharp-based pipeline, composition, premium bezel, soft glow, and recessed inner chamber, and make targeted refinements only. Primary visual goal: **subject breakout over the bezel** — extend the inner-chamber silhouette/micro-pattern **outside** the frame, not a second rear card or background frame behind the icon. Preserve top headroom so breakout elements (hats, ears) are not clipped. Never let a rectangular crop block, white background patch, or broad banner escape the frame; keep the ticker/signature bottom-right in black and always inside the frame; optically center the subject inside the chamber without flattening its depth. In `premium-v2` experiments, use fujilab/rembg subject masks for segmentation and a darker in-chamber background; keep breakout fully opaque (no translucent halo); suppress decorative corner glow (especially bottom-right); prefer brand-blue frame aura over white when tuning outer glow.

- For Telegram bot multi-step or progress responses, prefer a single editable message (e.g. one deploy progress list with per-contract green-check updates and basescan-hyperlinked addresses) over spamming new messages; menu selections should replace the prior message and provide a Back affordance. Keep command naming consistent across features (`/help`, not `/fullhelp`) and avoid gating Telegram-native flows on the Mini App when not required.

- For agent-facing / share / OG endpoints, prefer structured JSON with short, deterministic, high-signal strings and an explicit missing-context fallback envelope (`ok: false`, `error`, `missing: [...]`) instead of guessing fields.

- For KPR deprecation work, prefer hard-cut sunset execution (remove references/docs/workflows) over compatibility shims unless explicitly requested.

- For ad-hoc 3D model generation tasks (for example hologram GLBs), prefer the user's Hugging Face API/Space path over alternate providers unless they explicitly request a different provider.

- For bonding-curve visualizations, prefer green candlestick bodies for the bonding-curve spread with Sudoswap overlays, and keep direct chart interactions (mouse-wheel zoom around cursor plus click-drag horizontal panning).

- Ethos score UI should follow the official Ethos/Twitter-style treatment: use official label text and color bands, keep the pill slightly overlapping the avatar/logo, wrap the entire logo/avatar in the score-colored border when score data is meaningful, treat score `0` as neutral/unknown with a dash rather than negative styling, use standard green for online indicators, avoid overlapping availability dots, and use static, interactive hover cards that persist while hovered so profile actions are clickable.

- On the `4626.fun` marketing home (`frontend/public/immersive/index.html`), center the primary **Join the waitlist** CTA and keep hero/CTA copy concise — avoid redundant captions when the lockup already states product context. Reuse the dark, modern `/faq/how-it-works` visual language for downstream landing sections; merge or drop redundant Anatomy vs How-it-works (prefer scroll-driven How-it-works that reveals step 1 first and adds steps 2–4 on scroll), remove "The short version", and link to the FAQ page for deeper detail. Avoid hard dividers between landing panels — use gradients or soft transitions for seamless section flow.

- Marketing vault showcase/example carousels must not fabricate APY, TVL, or holder metrics; use real Zora creator names/tickers (e.g. `$jesse`, `$gabrielhaines`) and label slides as demo/example/illustrative only.

- Marketing footer/legal pages should avoid vertical line-streak backgrounds; use subtle gradients or patterns instead, and keep a consistent top-right nav set (Home, Docs, Security, About, Terms, Privacy, FAQ) across all marketing shells.

- **Explore creator detail pages:** keep page 1 hero identity-only; put stats in a scroll-scrubbed GSAP beat in the first `CreatorScrollBridge` (`CreatorImmersiveStatsBeat` + shared `creatorStatsModel.ts`) with **one metric revealed at a time** during the pinned scroll section (not a six-metric dashboard grid), then a compact static stats rail from the 3D scene onward; use a reduced-motion vertical stack fallback when `prefers-reduced-motion`.

- On `/explore/creators`, merge Ethos into the **Token** column — show the score on the avatar badge (`CreatorEthosAvatar`), make the Token header sortable for `?sort=ethosScore` (high → low), and drop the standalone Ethos column/subnav entry to save horizontal space.

- On Explore creator/content tables, fold fee-version copy (1% V4 vs 3% legacy) into the **Fees (24h)** column via a compact ℹ tooltip on the **column header only** (not per row) instead of a standalone Fee % column.

- On Explore list tables (Creators, Content, Trends), omit visible rank/index columns (# 1, 2, 3…) — let sort order convey ranking without ordinal labels.

- For Ethereum vault hero 3D, iterate offline in `tools/vault-images/` (Blender) with art direction **obsidian crystal ETH** (monolithic dark crystal) — **not** gold kintsugi/marble, and **no purple**: accents are Base-blue. Texture target is **obsdn.trade**-style: fine-grained, matte, very detailed — not glossy and not "cheap leather"; keep the bipyramid ETH silhouette large and upright but visually distinct from the bare Ethereum logo. Accent **veins flash only on lightning beats** (not always-on), and **remove the top halo / force-shield ring** (`ForceShieldMesh`). Map the crystal's six points to integrations via **brand colors, not logos** (top = Solana, center square = Base/blue, bottom = Ethereum; four mid-square points = Ajna, Uniswap, Charm, Zora), optionally with faint internal integration logos; label the object both **ERC-20 and ERC-4626** (token standard badge top-left). Production `4626.fun/` hero: Blender `ethereum_vault.glb` + marketing R3F island (`frontend/src/marketing/`, build `pnpm -C frontend build:marketing-vault` → `public/immersive/vault-hero/vault-hero.js`); fallback `public/immersive/vault.js` or `?hero=legacy`. Do not reintroduce Explore/creator-page R3F vault experiments. Runbook: `docs/operations/obsidian-vault-pipeline.md`.

- For the `/positions` social-signal chart (Hyperliquid-style room trade overlay), keep the timeline-events list and event-inspection panel on the **side** of the chart (not stacked above/below), make the chart fill the page width, and anchor hover tooltips to the cursor (not a fixed/random offset). Keep filter controls minimal and non-overlapping (and the **Host only** filter must actually show host messages); render room messages on the chart with the **sender's profile picture** as the marker (not a generic `W`/`RM` label); label position opens as **Open** with the entry size, use ☠️ for liquidated and 💬 for messages; final marker colors are **green for entry/add, red for close**; on hover show current price, the position at that timestamp, and P/L, differentiate **closed vs liquidated**, and keep host vs agent positions as separate entries (never collapse them into one market row).

- **`/arena/backtest` UI:** keep controls minimal — drop saved-run lists and sweep filter rows (health floor, chunk, cooldown); use direct USD inputs for long/short capital, one horizon picker (not select + duplicate pills), sliders for leverage/tuning where helpful, plain-language **bar size** copy (not "Resolution"), and premium full-horizon replay charts; 90-day runs should target finest available bars with honest coverage labels when minute cache is incomplete.

- For the Docusaurus docs site (`apps/docs-site`, `docs.4626.fun`), target a premium **Quiet precision** shell: minimalistic, modern, elegant, intuitive; extend homepage polish to inner doc chrome (sidebar, TOC, prose, code blocks); keep dark mode fully consistent with no default Docusaurus theme gaps; mobile sidebar and prose layouts must stay usable. Top nav uses the **4626.fun logo or wordmark as the home link** — no separate **Menu** label. Left sidebar and top nav follow **Learn → Launch** (not Launch-first). Footer stays modern/professional with the brand **blue + gold** palette only. Drop parenthetical side notes from page titles/subtitles (e.g. "(do not mix addresses)", "(short)") — keep copy elegant and standalone.

- Prefer governance naming **`veLottery`** (canonical; reject `veLotto` / `veChance`) and **`ve33`** (not `veVote`) in ve4626 identifiers and copy; see `docs/contracts/governance/ve-naming.md`.

- Prefer **lowest GitHub Actions usage**: keep heavy CI **PR-only** (no duplicate suite on `main` push), skip Dependabot-triggered heavy jobs, convert scheduled health monitors (auth-health, stuck-scan) and docs deploy to **`workflow_dispatch` / manual**, disable noisy Dependabot ecosystems (e.g. bun), and consolidate path-filtered guards — do not re-expand schedules or main-push re-runs without an explicit request.

- For Aristotle / Lean multi-target work on this machine, run **one proof target at a time** (sequential `lake build`, low `LEAN_NUM_THREADS`) — parallel Lean builds have crashed the user's computer.

- For future ecosystem lane integrations, prefer **real concrete names** (e.g. `FarcasterGaugeController`) plus shared `I*4626` capability interfaces for consumers — do not invent placeholder `FutureEcosystem*` types, and do not add an unsafe generic `execute(address,bytes)` policy controller.
