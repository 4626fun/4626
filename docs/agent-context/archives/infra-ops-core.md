- Isolated feature work often uses `git worktree add` under `/.worktrees/` at the repo root; that directory is gitignored via `.gitignore`.

- **Supabase identity consolidation (`supabase/migrations/20260714020000_*` + `20260714030000_*`):** Phase 1 merges `public.accounts` into `profiles` (`email_verified`; `account_linked_methods` / `account_zora_signals` FK → `profiles.privy_user_id`), migrates `creator_wallets` → `allowlist`, drops `accounts` + `creator_wallets`; Phase 2 renames `chat_directory_profiles` → `wallet_directory`, merges `creator_agent_wallets` + `creator_xmtp_agents` → `creator_infrastructure` (per-creator Privy keeper wallet + XMTP agent keys), and recreates `v_wallet_directory` as `wallet_directory` LEFT JOIN `profiles` by canonical wallet. - **New public tables require RLS.** Supabase's linter (`rls_disabled_in_public`) blocks on any public table without RLS. Pattern: `ALTER TABLE public.<name> ENABLE ROW LEVEL SECURITY;` in the migration, plus a restrictive deny-all policy `CREATE POLICY "deny_public_rest" ... AS RESTRICTIVE FOR ALL TO public USING (false) WITH CHECK (false);` to document "server-only" intent and satisfy the `rls_enabled_no_policy` info-level lint. Never use `FORCE ROW LEVEL SECURITY` — the table owner is `postgres` which is the same role our server connects as, and forcing breaks server writes. Server `DATABASE_URL` connections come in as `postgres` via the Supabase pooler and bypass RLS; `anon`/`authenticated` (PostgREST) default-deny when no permissive policies exist. The schema guard (`pnpm -C frontend guard:schema`) also catches raw DDL attempts that would bypass this rule.

- **Schema definitions are condensed to one source of truth.** There is only one Supabase project (`qajpnuvqlcfseghnldkl`). All DDL must originate in `supabase/migrations/`. The `frontend/db/migrations-legacy/` folder is an archived historical mirror (read-only; do not add files). Runtime `ensure*Schema()` functions must delegate via `frontend/server/_lib/db/schemaBootstrap.ts` using `ensureMigrationApplied(...)` (or named helpers such as `ensureAlfaclubSchema`, `ensureFinalAdditiveColumns`) instead of any raw `CREATE TABLE IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS` strings. The guard `pnpm -C frontend guard:schema` (implemented in `frontend/scripts/guard-no-raw-schema-ddl.mjs`) is enforced in CI and must pass locally before committing. See `docs/operations/supabase-schema-condensation.md` for the full current state, migration process, and archive details. This permanently eliminates the previous three-copy tax. **Live migration history lags repo file versions:** migrations applied through the Supabase MCP (`apply_migration`) are recorded under MCP auto-timestamp versions, so the live `schema_migrations` names don't match repo filenames — repo files under `supabase/migrations/` remain the canonical DDL documentation and must stay idempotent.

- **June 2026 Supabase table cleanup (DB ~15 GB → ~2.85 GB).** Dropped from the live DB: `creator_ethos_15min_snapshots` (6.7 GB) and `creator_ethos_hourly_snapshots` (5.4 GB) plus their snapshot/prune functions and cron jobs (Ethos health views rebuilt against `creator_ethos_projection` + daily snapshots + `mv_ethos_*`), the `creator_ethos_score_distribution` / `creator_ethos_by_*_bucket` tables, the orphan `query_temp_io_snapshots` telemetry table, and 8 dead scaffold tables (`thread_*` ×4, `payment_rail_attempts`, `base_address_activity_30d`, `farcaster_rollout_events`, legacy `public.alfaclub_chat_ingest`). Do not reintroduce 15min/hourly Ethos snapshot tables — daily snapshots + projection are the trend SSoT. `cleanup_log_retention()` was rebuilt: legacy 5-arg overload dropped (zero-arg cron call resolves unambiguously), wrong `created_at` column refs fixed (`alfaclub_metrics_snapshot` prunes by `snapshot_ts`), duplicate delete blocks merged via `LEAST()`, and `memory_snapshots` / `episodic_summaries` pruning is an **intentional no-op** (Eliza agent memory must not be silently deleted). **Follow-up index/snapshot optimization pass (`supabase/migrations/20260713030000_ethos_index_and_snapshot_optimization.sql`, DB 2.85 GB → ~2.49 GB):** dropped the duplicate `creator_coins` rank index and the single-value `chain_id` index, removed the duplicate projection score index, reindexed `telegram_link_telemetry_events`, and rewrote `snapshot_creator_ethos_daily()` to snapshot **only scored creators** (~15K rows/day instead of all ~84K projection rows; `creator_ethos_daily_snapshots` pruned to scored rows under 90-day retention) — do not revert it to snapshotting the full projection. **Third pass (DB → ~2.0 GB, behavior/maintenance only):** the deprecated Ethos chart matview layer + endpoints were retired (`20260713110000_retire_ethos_chart_matview_layer.sql`); the full `recomputeCreatorCounts` creators reconcile is gated by `maybeRecomputeCreatorCounts` with a `creators_reconciled_at` watermark in `creator_metrics_state` (runs at most every 6h, tunable via `CREATOR_METRICS_RECONCILE_INTERVAL_MINUTES`; the explicit repair script still calls the ungated version) — do not put the ungated full pass back on every sync tick; and churn-heavy tables (`creator_coins`, `zora_csw_owners`, `creators`, `ethos_userkey_scores`, `creator_ethos_projection`, `creator_ethos_daily_snapshots`) carry per-table autovacuum tuning (`20260713130000`) so index bloat does not regrow. The remaining ~2 GB is legitimate data — dropping audit columns (e.g. `zora_csw_owners.creation_tx_hash`) or pruning unmatched CSW rows are explicitly rejected data-loss options.

- **Profile merge moves arch-b tables too.** `executeProfileMerge` in `frontend/server/_lib/identity/profileMerge.ts` moves `points`, `referral_conversions`, `profile_wallets` (Step 3b, counted as `walletRowsSwept` in `ProfileMergeResult`), `command_issuer_execution_context` (re-key or drop based on whether `to` already has one), and `command_issuer_daily_spend` (sum per-ymd) in addition to the referee repointing. Any NEW table that has `profile_id` as FK and represents per-profile state must be added to the merge primitive, otherwise merges leave orphaned rows on tombstones.

- **`profile_wallets` role flags must be forced FALSE on any sweep/salvage INSERT.** Partial unique indexes (`profile_wallets_one_canonical`, `_one_embedded_eoa`, `_one_primary`, `_one_canonical_solana`, `_one_operational_solana`) enforce at most one canonical row per profile. When moving rows from a tombstone (or any non-authoritative profile) onto the canonical target, set `is_primary`, `is_canonical_smart_wallet`, `is_embedded_eoa`, `is_canonical_solana_wallet`, and `is_operational_solana_wallet` to FALSE on the migrated rows, tag with `metadata.salvagedFromTombstoneId` for audit, and use `ON CONFLICT (profile_id, address) DO NOTHING`. The target's own canonical row stays authoritative; never displace it from a secondary attachment.

- **`solana_ovault_mesh` is not a Phase 3 vault strategy allocation.** Treat it as a Phase 2b routing entitlement; there is no `setStrategyMaxAssets` or `addStrategy` calldata to apply for this non-strategy entitlement.

- **Pipe A uses a per-creator registry peer.** Phase 2 bridges 30% ShareOFT through LayerZero. Every creator must have a non-zero `Registry4626.setRemoteOFTPeerBytes32(creatorToken, solanaEid, peer)` entry before finalize; the removed batcher-global peer and Twin adapter are never fallbacks.

- **4626 has two vault-share burn lanes — do not conflate them.** ShareOFT trade-fee revenue hits `CreatorGaugeController` and splits on distribute: 69% ■ ShareOFT to lottery reserve, 21.39% ■ ShareOFT to voters (`ve4626VoterRewardsDistributor`), 9.61% ▢ vault shares burned (no keeper harvest). Creator Coin external revenue in `payout_router` mode flows `PayoutRouter.convertAndQueue` → vault deposit to `CreatorVaultShareBurnStream` → permissionless weekly `checkpoint()` drip. Keepr harvest automates only the PayoutRouter lane; `drip()`/`checkpoint()` are public.

- **Keeper job coordination is the KPR-independent fallback lane, but not yet a full KPR replacement.** `public.keeper_jobs` is created by `supabase/migrations/20260506221000_keeper_job_coordination_queue.sql` with deny-all RLS; `/api/keeper/jobs/*` handles enqueue/claim/complete/status/health/run behind machine auth or cron auth; `pnpm -C frontend keeper:jobs:worker` claims `internal_api`/`noop` jobs using `KEEPER_COORDINATION_BASE_URL` and `KPR_API_KEY`. Legacy **`/api/cre/*` is removed** — `internal_api` payloads must use `/api/keeper/*` or `/api/keepr/actions/*` only (`docs/operations/keeper-http-api.md`). Current confirmed coverage is sweep/tend/report/**rebalance**/payout multi-vault fan-out plus sweep -> mark-settled follow-up. **Payout-router harvest** (`POST /api/keeper/payout-router-harvest` + KPR `payout-router-harvest`) is code-complete for `payout_router` vaults, but Vercel cron enqueue alone does not run harvest — `/api/keeper/jobs/run` cron (every 5 min) or an always-on **`keeper:jobs:worker`** or Railway KPR must claim jobs. **Pick one primary executor:** Vercel `keeper_jobs` payout fan-out (`KEEPER_ACTIVE_VAULT_ENQUEUE_ENABLED=1`) with Railway `KPR_PAYOUT_ROUTER_HARVEST_ENABLED=0`, or direct KPR harvest with payout omitted from Vercel workflows — do not run both against the same router. Greenfield phase 2 now wires `setBurnStreamAuthorizedQueuer(router)`; per-vault treasury `setKeeper` + swap paths self-heal via `maybeAutoSetupPayoutRouterTreasury` (Safe-batched `setKeeper` + `setSwapPath`) when `PAYOUT_ROUTER_TREASURY_AUTO_SETUP=1` — until setup runs, ZORA accumulates safely in the router and harvest skips. **Production payout harvest is enabled:** `KEEPER_ACTIVE_VAULT_WORKFLOWS` must include `payout` (it was silently missing) plus `PAYOUT_ROUTER_TREASURY_AUTO_SETUP=1` and `KEEPER_ACTIVE_VAULT_PAYOUT_RECIPIENT_MODE=payout_router`; gauge-mode vaults (e.g. AKITA) correctly produce no payout jobs. **`enqueue-active-vaults` honors the per-vault kill switch:** the enqueue query excludes vaults whose `keepr_vault_automation` row is `automation_enabled=false` or revoked (vaults without a row stay enabled); pausing a vault is a one-row update plus cancelling already-queued jobs — AKITA's scheduled tend/report/rebalance/payout automation is currently paused by operator this way. `process-keepr-actions` queue processing, bridge-integrity, Ajna/Charm, strategy-signal listener, and Solana workflows still need explicit replacement lanes. Enable cross-strategy rebalance in the worker with `KEEPER_ACTIVE_VAULT_WORKFLOWS=...,rebalance,...`. Keep privileged signing behind existing machine-auth endpoints, keep worker paths allowlisted to `/api/keeper/` and `/api/keepr/actions/`, and monitor non-zero retry/failed/expired-claim counts once carrying production work.

- **`indexer/` is the `@4626/zora-csw-indexer` standalone service** that powers targeted agent-install outreach. It scans `ZoraSmartWalletCreated` events on `ZoraAccountManager` (`0x0Ba958A449701907302e28F5955fa9d16dDC45c3` on Base), upserts into Supabase `zora_csw_owners` (`csw_address` PK, `initial_owners`, `current_owners` re-read via `ownerAtIndex(i)` since owners can drift after `addOwnerAddress`), and classifies each owner EOA into `zora_csw_owner_class` via `src/classifyOwners.ts` using a nonce heuristic: `base_nonce == 0 AND mainnet_nonce == 0 → likely_privy_embedded`, otherwise `likely_extension_eoa`. `src/crossReferenceFarcaster.ts` joins each EOA with Neynar verified-addresses to populate `farcaster_fid` / `farcaster_username`. Both tables are RLS-enabled, service-role-only; the indexer owns the sole write path. Prefer classifying top-N-by-`mainnet_nonce` extension owners first when running campaigns. `mainnet.base.org` caps `eth_getLogs` at 10k blocks and rate-limits enrichment — use a paid `BASE_RPC_URL` (Alchemy/QuickNode/matrixed.link). Entry points: `pnpm poc` (recent 100 CSWs), `pnpm enrich` (refresh `current_owners`), plus classify/cross-reference runners in `src/`. Do not reintroduce a Privy-based signing flow inside the Zora content coin — the indexer exists specifically because the sandbox path was abandoned; see `README.md`.

- **`zora_csw_owners` dominates Supabase load (~1.5M rows / ~1.5 GB).** Seq-scan-heavy jobs are the main risk; runbook: `docs/operations/supabase-zora-db-optimization.md`. Maintenance migration: `supabase/migrations/20260518220000_zora_table_maintenance.sql` (`lower(csw_address)` index, outreach partial index, weekly `pg_cron` `VACUUM ANALYZE`). `indexer/src/classifyOwners.ts` defaults to `CLASSIFY_MAX_ENRICHED_ROWS=25000` plus optional `CLASSIFY_MIN_CREATION_BLOCK` — use `CLASSIFY_UNLIMITED=1` only for intentional full passes. `frontend/scripts/ethos-zora-backfill.ts` uses `pg_class` row estimates for progress (no `COUNT(*)`).

- **Zora CSW owner Ethos scores are cached on `zora_csw_owner_class`.** The live schema and repo migrations add `ethos_userkey`, `ethos_score`, `ethos_level`, and `ethos_score_updated_at`; `/api/v1/zora-csw/enrich-cron` refreshes owner scores through `refreshZoraOwnerEthosScores` with `INDEXER_ETHOS_ENRICH_BUDGET` (default 250, `0` disables). Keep this as a latest-score cache for app/dashboard reads; Ethos itself exposes `/score/history` for score timelines and `/score/updates` for change-driven refreshes, so only add a local append-only history table if product needs independent audit snapshots.
