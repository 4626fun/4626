## Learned User Preferences

- Loading and progress labels must match the actual action context — reserve action verbs (e.g., "Deploying...") for when the action is executing, not for page navigation or initial load, keep unrelated controls (for example `Reset`) from switching labels during other in-flight actions, and prefer `PixelWaveLoader`-style motion for waitlist/account-setup loading over text-scramble, rotating-square, or four-square placeholders that feel laggy or distracting. After waitlist email OTP verify, show an explicit loading state during the long post-verify → next-page transition — do not leave users on a silent hang.

- App bootstrap should use one unified loading shell with one message — avoid flicker between session sync and route/page load overlays; prefer subtle route fade-in/out transitions over hard cuts between screens. Use `AppLoadingOverlay` debounced hide (~280ms), `app-loading-scroll-lock` + `scrollbar-gutter: stable`, `AppLoadingBootstrapGate` to keep route content out of the DOM during bootstrap (with ~220ms content fade-in when loading clears), and gate `PrivyClientProvider` children during Privy init — do not add per-route custom Privy/init panels (DeployVault removed its separate "Initializing authentication" block). Route changes use `PageTransitionOutlet`; nested tab/sub-route switches (Explore, Admin) share `PageTransitionNestedOutlet` instead of duplicating transition wiring.

- For waitlist/account surfaces, consolidate closely related panels (for example "Linked Identities" and the link-to-earn points panel) into one compact section and use real platform icons instead of text labels for channel rows.

- Prefer consolidating Privy OAuth/account-link flows into shared `frontend/src/lib/privy/` modules (`providerLink.ts`, `accessToken.ts`, `safeHooks.ts`) instead of parallel per-feature hooks — user explicitly asked to dedupe waitlist vs account-setup link code. Prefer deleting or consolidating brittle remount / loopback `clientId` / mode hacks over adding more workarounds; keep one invariant-safe Privy setup and do not ship a second account model. **Never mention Base/Coinbase sub-accounts** in docs, UI copy, or explanations (including as “optional future infrastructure”) — the only model is parent CSW + Privy embedded EOA (user signer) + Privy server wallet (headless automation).

- Keep waitlist point awards as even integers so the 50% referral passthrough stays whole, and prefer framing the recurring daily earn action as a social share on X / Farcaster / Telegram rather than a "lottery check-in"; per-submission AMOE entry points should stay removed.

- Waitlist/marketing shells on `4626.fun` and `app.4626.fun` must expose an explicit **Sign out** control (for example `WaitlistFlow` / setup tray) so users can break Privy/session auto-restore loops; redirecting to `/waitlist` after sign-out is acceptable. On mobile, render sign-out as red text without a heavy border and keep header actions on one line.

- Waitlist leaderboard identity rows should show Basename when available, otherwise the canonical CSW address — never the Privy embedded EOA; use the Coinbase logo for CSW affordances (not a generic CSW badge) and avoid generic labels like "creator" for the primary identity string.

- Waitlist wallet/messaging UI must branch on `resolveWaitlistConnectTrack` using server account population (`executionTrack`, `canonical_source`), not only `isBaseAppInAppContext()` — a Zora-linked user browsing inside Base App's webview is still Zora and must finish owner install before CSW messaging.

- Waitlist signup stays **email-only Privy** by default; the path is **Continue → setup workspace** with no blocking `connect-base-app` step or dual Base-vs-email auth on `/waitlist`. Base App wallet connect belongs in the setup workspace as an optional post-verify nudge and must not block joining or auto-bootstrap on page load. **Enter App** stays admin-approval gated — optional Zora/Base/signing must not block waitlist join. Email-collision recovery (`RECOVERY_REQUIRED_EMAIL_BOUND`) must sign out the colliding Privy + server session before existing-account handoff — reusing a stale Privy token recreates the waitlist redirect loop. Never display a stored pre-auth email hint (`cv:waitlist:verified-email-hint`) as a live Privy session — use `resolveWaitlistPrivyDisplayEmail` for copy; hints are for OTP continuity only. **Returning wallet sign-in** (`WaitlistReturningWalletSignIn`, "Already joined?") is a surgical optional lane for users who already completed email OTP and want to reconnect an external EOA — initial signup must still mint Privy ID + embedded EOA via email; wallet-only Privy login must not replace that first-time path. Keep `createOnLogin` omitted on both waitlist Privy modes (avoids localhost/iframe auto-create races), but **explicitly call `ensureEmbeddedWallet()` in the join tail before `bridgePrivySession`** so brand-new email signups have an embedded EOA before session mint — omitting both auto-create and the explicit ensure causes session-bridge 400s for zero-wallet users. Expose a **Cancel wallet sign-in** escape hatch when the returning-wallet busy state hangs (Privy modal never opens on localhost extension collisions).

- Use "waitlist" for app-access queue copy and "whitelist" for vault-deployment eligibility copy; surface the one-deploy-per-wallet-per-deployment-version cap explicitly in deploy UI.

- Waitlist approved/linked state: replace generic blue checkmarks with the **4626 "4" logo**; make **Enter App** a tactile 3D CTA; show per-link **Edit** affordances and game-style floating `+points` popups when link rows collapse into the Earn Points header. The `appAccepted` logo ring glow is **brand blue** (`rgb(var(--brand-primary))`), not green — user explicitly rejected the emerald/green ring as off-brand and asked for it to glow blue instead.

- Waitlist modal/panel chrome should feel seamless — avoid obvious heavy top/bottom borders or boxed framing on the waitlist component.

- Approved waitlist workspace layout: on desktop, pin the leaderboard as a left rail and group chat as a right rail; keep the layout mobile-friendly. For joined/approved waitlist chrome, put **points + account/onboarding in a top-right corner tray** matching the app `AccountTray` (identity, linked accounts, owner-install/setup, points tabs) — not a large inline post-join card body. Use the **wagmi-free waitlist adapter** (`WaitlistAccountTray` / `useWaitlistCanonicalIdentity`); do **not** mount `WagmiProvider` on marketing `/waitlist` just to reuse app tray hooks (extension `window.ethereum` races and Coinbase Wallet SDK COOP probes already broke email OTP there). Tray chrome preferences that stuck across iterations: prefer the linked **creator-coin** (`$akita` / Zora coin art) as the tray hero over the CSW logo when available; keep tray width ~**30rem** so full contract addresses stay on one line; show **full** wallet addresses (not truncated) in the tray; place **Sign out** / **Disconnect** as red right-aligned actions on the matching `CanonicalIdentityDropdown` / wallet rows (not orphaned under points); keep the tray footer consistent with the app tray (**Help / Accounts / Settings / Sign out**); keep primary **Enter App** on the main approved waitlist surface (not only in the tray footer); style points to fit the tray (no heavy BeamCard); `EmbeddedSignerMark` should use the large 4626 **"4"** with a small Privy badge bottom-right (same badge pattern as CSW+Zora); green owner-status dots sit on the **right** of role icons when that key is an authorized CSW owner.

- Approved waitlist users (`appAccepted`) must still see the Link X panel and post-link X engagement steps — do not hide Twitter linking once the user is approved for app access.

- Waitlist social proof ("X already joined" overlapping avatars + count) should stay visible through the **entire waitlist flow** (signup, on-list, approved), not only on specific phases; on the signed-out waitlist page place it **between the email card and the "Already joined?" wallet sign-in row** (not above the headline/subtitle). Show real member profile photos when available (Zora basename avatar → Zora avatar → profile avatar → preprov Farcaster pfp / linked external wallet), not only brand gradient placeholders — size slots to the real avatar count (no empty blue placeholder circles). Prefer a simple smooth motion: avatars enter so the count **ticks up** (not a vacuum/suck into the number), keep the count text aligned with the "already joined" label, and make the **"N already joined" → "already joined"** copy transition subtle. When identity resolves, each avatar should be hover/focus-identifiable (tooltip with @handle, basename, or short CSW) and link out to the member's Zora profile or Basescan — linkable address is canonical CSW or external EOA only, never the Privy embedded EOA. Hide the "See leaderboard" link during email/signup phases.

- Waitlist email input should turn green when the address is valid, with an elegant animated transition into the next phase; the "Powered by Privy" footer should include the Privy symbol (`/brands/privy-symbol-white.svg`). OTP digit fields and surrounding chrome must not show green/success glow until verification has actually completed — including any glow around the digit count/indicators.

- Identity presentation should use one shared resolution order everywhere (chat rail, chat windows, waitlist leaderboard, welcome greeting, and account chips): **Zora profile -> Basename -> ENS -> 0x fallback** with consistent avatar sourcing and no slow-loading regressions that replace known labels with raw addresses. Never treat address-shaped strings (`0x…`) as Zora handles — no `@0x…` from the Privy embedded EOA on "Welcome back" or similar copy.

- For multi-step onboarding/wizard flows (e.g. waitlist linking steps), prefer one shared `AnimatePresence` cross-fade/slide with `layout`-animated height changes between steps over abrupt swaps — unify the easing/duration curve across every step transition in the flow (including any pre-existing OTP/code-entry step) rather than mixing a fast linear fade with slower eased ones; list rows that appear/reorder (e.g. newly-linked accounts) should animate in/out and reflow smoothly too.

## Learned Workspace Facts

- **Robinhood Chain remote ShareOFT expansion (4663 / EID 30416):** Base stays the vault-accounting hub — V1 is remote `CreatorShareOFT` only (`isHub=false`, `hubEid=30184`), no CreatorOVault/gauge/strategies on Robinhood; uses non-common LZ EndpointV2 `0x6F475642a6e85809B1c36Fa62763669b1b48DD5B` (needs `OFTBootstrapRegistry` v2 CREATE2 salt); Base↔Robinhood shared DVNs are LayerZero Labs, Nethermind, Horizen, BitGo, and Canary at 3-of-5 — do not reuse Base↔Solana 6-of-9 DVNs.

- `GET /api/waitlist/stats` serves live waitlist count data for urgency display (`signedUpCount` + up to four recent-member `avatars` from `fetchRecentMemberAvatars` in `_stats.ts`); waitlist capacity uses configurable 100-slot tiers with dynamic "Only X spots remaining!" messaging. **`getWaitlistMemberCount()` in `waitlistLeaderboard.ts` is the SSoT** — counts verified-email profiles excluding merged tombstones (`merged_into_profile_id IS NULL`); both `/api/waitlist/stats` and leaderboard `totalCount` must use it so counts stay aligned. `WaitlistFlow` polls stats every **30s** and refetches immediately after a successful join.

- **Zora profile lookup for 4626 accounts** uses shared `zoraProfileIdentifier` helpers (server `frontend/server/_lib/zora/zoraProfileIdentifier.ts`, client mirror `frontend/src/lib/zora/zoraProfileIdentifier.ts`) with seed priority: handle → Zora cross-app → **canonical CSW (`profiles.csw_address`)** → external EOA → primary wallet → embedded EOA (embedded skipped when CSW is known). Account-scoped flows (`walletSync`, `accountsIdentity`, waitlist bootstrap/preprovision, `useAccountZoraProfile`, deploy/agent register) must not query the Privy embedded EOA when CSW exists; public `GET /api/zora/profile?identifier=` remains a pass-through for explore/chat.

- Canonical CSW owner-install sponsorship accepts `addOwnerAddress` self-calls for the authenticated Privy embedded EOA without requiring deploy-session signer state; keep deploy-session checks scoped to deploy-session automation paths.

- **`resolveWaitlistConnectTrack`** (`waitlistFlowState.ts`) splits waitlist connect/messaging into `base-app-direct` | `zora-owner-install` | `not-ready`. Base App track uses `prepareWaitlistMessagingWallet` → Coinbase connector → canonical CSW → XMTP in one CTA; Zora track stays read-only Zora link → owner install → embedded-EOA messaging. Population (a) can join the waitlist by email only; group chat can unlock via optional Zora/Base App CSW **or** auto-provisioned Privy parent CSW (`WaitlistWalletProvision` / `useEnsurePrivySmartWallet`) plus browser owner install (`WaitlistPrivyWebOwnerInstall` / `usePrivyCswWebOwnerInstall`) — `not-ready` copy must not say "Enable 4626 signing" when no CSW exists yet.

- `/api/onboarding/bootstrap` and `/api/accounts/me` both expose `executionTrack` and `privyEmbeddedEoaIsOwnerOfCanonicalCsw` as the source of truth for execution-track decisions; clients must read these fields rather than recompute routing from wallet state. Server profile resolution for both endpoints must use `listProfileIdsForPrivyUser` (alias-first), not a direct `profiles.privy_user_id = ?` lookup — merged/alias Privy users otherwise miss canonical CSW rows and swap gates falsely show execution-setup-required. Account-setup surfaces (`useAccountSetupController`, `/add`) must merge both via `mergeAccountMeWithBootstrap` — reading `/api/accounts/me` alone can miss canonical CSW already on the profile. **These two endpoints keep coming up as "aren't these duplicates, can we merge them?"** — they're not: `/accounts/me` is a DB-only identity/points read, `/onboarding/bootstrap` resolves execution-track signals via a heavier, separately-cached (30s TTL) canonical-CSW on-chain owner check; merging the handlers server-side wouldn't reduce any actual work and would blur that wallet-invariant separation. `useAccountMe.ts`'s `fetchAccountMe` fetches both **concurrently via `Promise.all`** (split into a standalone `fetchAccountMePayload` helper) rather than sequentially, since bootstrap never depends on the `/me` response — that's the real, safe optimization here, not a backend merge.

- **Waitlist bootstrap auto-adopts wallet-bound Privy collisions** when the active session's wallets match the canonical profile (`runWithWaitlistWalletCollisionAdoption` in `emailCollisionAdoption.ts`): if `WALLET_BOUND_TO_CANONICAL_EMAIL_PROFILE` fires but connected CSW/embedded EOA owns the target row, seed `privy_user_aliases` and retry instead of looping "Use existing account" — distinct from email-collision sign-out recovery.

- **Waitlist returning wallet sign-in uses dual Privy modes on `/waitlist`.** Default `PrivyClientProvider` runs `mode="waitlist-email-only"` (no external wallet connectors during email OTP — Coinbase Wallet SDK and WalletConnect must stay off that path or extension races destabilize OTP). Clicking **Sign in with linked wallet** **key-remounts** the provider (`key=wallet-${attempt}`, not in-place mode mutation) to `waitlist-returning-wallet` + `ethereum-only`, mounts `WaitlistReturningWalletSignInRunner`, and sets `showWalletLoginFirst`. Returning-wallet connectors are **WalletConnect + EIP-6963 detected wallets only** (`WAITLIST_RETURNING_WALLET_LOGIN_LIST`: `detected_ethereum_wallets`, `wallet_connect`) — **Coinbase Wallet SDK is excluded** on this path to avoid localhost `window.ethereum` fights and failed COOP HEAD probes. Both waitlist modes **omit embedded-wallet `createOnLogin`** (localhost/iframe safety), but email-join must still provision an embedded EOA before session mint via best-effort `ensureEmbeddedWallet()` in `establishWaitlistSessionAfterPrivyAuth` (non-fatal if create fails; returning-wallet path stays external-EOA only and may omit the ensure callback). **Do not remount into `waitlist-wallet-joined` immediately after email OTP** — that remount plus loopback `clientId` churn can restore a different Privy session while the 4626 cookie stays on the email-join user, so later wallet SIWE / `/api/accounts/link` attaches Base/CSW to the wrong `privyUserId`; defer wallet-joined remount until explicit wallet-connect intent. **Joined waitlist UI requires both** the HttpOnly `cv_auth_session` cookie **and** `privy.authenticated` (`resolveWaitlistJoinedSessionAddress` in `resolveWaitlistJoinedSession.ts`); an orphan cookie without Privy shows the signed-out email view (0 pts, empty linked identities). Debounced orphan cleanup via `shouldClearOrphanWaitlistServerSession`; gate `useAccountMe` until actually joined. After wallet sign-in, call `invalidateAccountMeCache()`; bootstrap must attach wallet-only Privy users to existing `profiles` / linked-wallet rows when Privy omits verified email.

- **Waitlist Privy session bridge (`waitlistPrivySession.ts`).** After auth, treat the address returned from `bridgePrivySession` → `/api/auth/privy` as session truth — do not require an immediate `/api/auth/me` confirm (rate-limit backoff and stale Bearer shadowing cause false "session still syncing"). Call `ensureEmbeddedWallet` (when provided) after the Privy token is confirmed and **before** `bridgePrivySession` so zero-wallet brand-new signups do not 400. **Do not call full Privy logout before wallet reconnect when a live access token exists** — reuse the token and bridge; if `authenticated` but tokenless, clear the 4626 server cookie only (`shouldLogout: false`). Skip a second `login()` when already authenticated; poll for the access token, then bridge. Rollback after failed bridge should avoid unnecessary Privy SDK logout (400 noise on `sessions/logout`).

- **Privy server wallet create/provision must use the `wallets` array API** (`wallets: [{ chainType: 'ethereum', policyIds: [] }]`) — deprecated wallet-count parameters are rejected and surface as `auth.privy.io` passwordless/authenticate **422**, leaving waitlist join stuck with `privyAuthenticated: true` but no 4626 session.

- **4626 admin waitlist (`/admin/waitlist`, `/api/admin/waitlist/list`) is not the Privy dashboard user list.** Admin rows come from Supabase `profiles` / waitlist bootstrap (`POST /api/waitlist/bootstrap`); Privy dashboard users can exist before bootstrap completes. Users in Privy but missing from admin usually mean bootstrap never finished, bootstrap failed (check Vercel `waitlist/bootstrap` logs), or admin is pointed at a non-production DB — not a Privy sync bug.

- `/accounts` redirects to `/waitlist`; the advanced account-setup controls live in `WaitlistAdvancedSection` mounted inside the waitlist page (no separate `/accounts` UI).

- `referral_passthrough` is a first-class `waitlist_points` source written by `recordReferralPassthrough` in `frontend/server/_lib/onboarding/waitlistPoints.ts`; it credits referrers with 50% of every point the referee earns, and every scoring query (`waitlistLeaderboard.ts`, `waitlist/_position.ts`, `waitlist/_referrer.ts`, `accountsIdentity.ts`) must include this source. - **The Privy localhost marker-cookie assertion pattern (`loopbackSessionMarkerShim.ts`) must be applied at every Privy SDK call site, not just token reads — this is a recurring root cause, not a one-off.** `providerLink.ts`'s `unlinkPrivyProvider`/`linkPrivyProvider`, `WaitlistFlow.tsx`'s Zora `unlinkCrossAppAccount` call, and `privyAuthorizedWalletRpc.ts`'s `postAuthorizedWalletRpc` (used by XMTP `personal_sign`/`eth_signTypedData_v4`) each 401'd on localhost until they asserted the `privy-session` marker immediately before the SDK call, matching the working `refreshPrivyEmbeddedSignerSession` pattern. A 401 on one Privy call (e.g. editing a linked identity) can trigger `resetPrivyLoopbackSessionAfterAuthFailure()`, wiping the whole local session and cascading into an unrelated-looking XMTP connect failure moments later — make sure `/api/v1/siwe/unlink` (not just `siwe/link`) is in the 401-reset matcher. Separately, Privy's `unlinkWallet`/`unlinkTwitter` SDK methods take plain strings, not `{ value }` objects, and Twitter unlink needs the Privy **subject**, not the display handle.

- **Unified 4626 room chat:** AlfaClub remains the message/membership authority; Telegram and XMTP are data-driven room adapters via `alfaclub.room_channel_bindings` + `cross_channel_ingress` and `frontend/server/_lib/alfaclub/roomChannelBridge.ts` (not a hard-coded room-1659-only module). Native panel: `GET|POST /api/v1/alfaclub/room-chat` + `/rooms?tab=chat`. Command replies stay on the Privy JWT WebSocket lane; keep the authenticated AlfaClub API lane for validated Telegram/XMTP ingress and non-command posts (do not delete the API path to fix duplicate command replies). Canary: `docs/_internal/operations/alfaclub/unified-room-chat-canary.md`.

- **Paid/keyed Base RPC must not ship in the browser bundle via `VITE_BASE_RPC`.** Keep Alchemy, Coinbase Developer, and Matrixed URLs server-side (`BASE_RPC_URL` / `BASE_READ_RPC_URL`) behind session-authenticated `/api/rpc`; `frontend/src/lib/base/baseReadRpcPolicy.ts` `isBrowserRestrictedBaseRpc` forces those patterns back to the same-origin proxy. Local fork reads may still use loopback `VITE_BASE_RPC`.
