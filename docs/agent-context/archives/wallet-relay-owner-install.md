## Learned User Preferences

- Rename user-facing labels that describe CSW owner-install flows to match the parent-CSW embedded-owner architecture (e.g. "Enable 4626 signing" / **"Enable 4626"** rather than "Connect Coinbase Smart Wallet"). Default waitlist Step 2 targets **parent CSW** embedded-owner install (`legacy-owner-install`). Prefer **one visible Base App/passkey signature** that installs the Privy embedded EOA as a CSW owner, then **silently** install the Privy server wallet via embedded-EOA-signed `canonical4337`; after the embedded EOA is on-chain, retries must be idempotent and must not demand another passkey.

- When adding Base App direct XMTP/swap lanes, keep the Zora read-only → Privy embedded-EOA owner-install path unchanged; `base-app-direct` is additive for `canonical_source === 'base_account'` only — do not skip owner install for Zora `wallet_sync` users.

- For CSW owner-setup and deploy flows, prefer click-first Base App deep-link/prolink or parent-CSW Relay owner-install (`/waitlist?setup=owner-install`, `AddOwnerSigningPanel`). Avoid external-EOA fallback paths, and if canonical signing is unavailable, fail with explicit guidance rather than forcing long manual EOA signature sequences.

- When debugging wallet, Base App, Relay, or Coinbase Smart Wallet behavior, be explicit about what is known, observed, and still uncertain; do not present inferred wallet/API behavior as fact without runtime evidence.

## Learned Workspace Facts

- Perplexity-ready skill packages live under `docs/perplexity/perplexity-skills/` as one-folder-per-skill bundles with a `SKILL.md` entrypoint, and are commonly shared as `.zip` archives.

- **One-signature Enable 4626 activation (product path):** resumable two-stage flow on the parent CSW — (1) visible Base App UserOp self-calls `addOwnerAddress(embeddedEoa)`; (2) after on-chain `isOwnerAddress(embeddedEoa)`, silent sponsored `canonical4337` UserOp self-calls `addOwnerAddress(serverWallet)`. XMTP/server automation stays keyed to the parent CSW identity (not either EOA). Status/completion endpoints stay read-only and idempotent; partial-ready after embedded ownership must resume silent server-owner install without another passkey.

- **`base-app-direct` is an additive server execution track** gated on `profile_wallets.canonical_source === 'base_account'` only. Zora `wallet_sync` accounts with CSW + embedded EOA but no owner install must stay `executionTrack: 'none-yet'` / `embedded_owner_not_installed` — never short-circuit Zora users into `base-app-direct`. `addOwnerAddress` from third-party 4626.fun/app.4626.fun dapps is blocked for Base App-managed CSWs; population (b) uses parent CSW + Base App connector signing for XMTP/swap, not embedded-owner install (deploy still requires `legacy-owner-install`).

- XMTP new-conversation search resolves a Basename suffix (e.g. typing `akita` matches `akita.base.eth`) and should render the Base App display name and profile picture for the canonical Coinbase Smart Wallet address, not a shortened hex address. Canonical CSW remains preferred for DMs, but if production XMTP says the canonical CSW has no inbox and the original Basename-resolved address does, fall back to that original reachable address and keep it as the chat peer.

- Base App CSW owner-action probes and prolink owner-add flows should use the prepared-calls lane (`wallet_prepareCalls` → sign the replay-safe/prepared payload → `wallet_sendPreparedCalls`). Signing the raw `userOpHash` directly is not sufficient for Coinbase Smart Wallet owner validation. Canonical CSW self-auth sessions where `walletClient.account` is the CSW must instead route through the direct replayable lane (`eth_sendTransaction` from CSW to CSW with `executeWithoutChainIdValidation`) so popup self-call guards are not selected.

- Direct browser WebAuthn from `4626.fun` cannot assert Coinbase Smart Wallet passkeys issued under Coinbase RP IDs such as `keys.coinbase.com` / `sign.coinbase.com`; keep passkey-direct `navigator.credentials.get` UserOp lanes disabled or diagnostic-only, and route passkey-owned Coinbase CSW owner actions through Coinbase/Base App prepared-call context.

- CSW add-owner Relay paths must stay strict about the selected owner slot: replayable self-built UserOps need a WebAuthn/passkey owner signature for the CSW owner slot they validate against, and relaxed session-key/ECDSA wrappers can revert because `ownerIndex` selects the exact `ownerAtIndex(...)` validation path.

- `/api/relay/quote` is a focused Relay deposit-discovery helper for Base mainnet `EntryPoint.handleOps(...)` calls; it requests Relay `/quote/v2` with `explicitDeposit: true` after signed `handleOps` calldata exists, so CSW owner-add probes can inspect required Relay deposit/order context before execute.

- **Relay Vaults (`relayprotocol/relay-vaults`) is not Relay Settlement / relay-kit.** The relay-vaults repo is an ERC-4626 LP/bridge product; CSW owner mutations use Relay Settlement quote preview + manual Part 1 submit (`preview-add-owner`, `executeOwnerMutationViaRelay`), not relay-kit `execute()` for CSW self-auth. Guide: `docs/_internal/operations/operations/wallet/relay-owner-mutation-kit-guide.md`; evaluation: `docs/research/relay-vaults-evaluation.md`.

- **CSW Relay Part 1 uses Depository `depositNative`, not router multicall or relay-kit `execute()`.** Parent-CSW self-auth submits preview `userCall` → `RelayDepository.depositNative` at `0x4cD00E38…` (selector `0x49290c1c`). Do not use Relay Settlement **RelayRouter** (`0xb92fe925dc43a0ecde6c8b1a2709c170ec4fff4f`) or its `multicall` (`0xcd6e13f7`) for CSW Part 1 or embedded `addOwnerAddress` — the CSW sees the router as `msg.sender`, not `address(this)`, so owner checks fail and Relay never indexes. Echoed EXACT_OUTPUT wei (~2.88e12) underfunds Part 1 deposits. **`addOwnerAddress` must be a CSW self-call** (EntryPoint UserOp or `wallet_sendCalls` to the CSW); guard with `assertAddOwnerSelfCallShape` in `frontend/src/lib/wallet/addOwnerCallShape.ts` (used on the `/add` Base App owner install surface). **In Base App, skip `wallet_sendCalls`** for Relay Part 1 (it auto-injects USDC paymaster); use prepare → strip paymaster → bundler only, and **fail closed** if a landed Part 1 UserOp has any paymaster — Relay Part 2 requires paymaster = 0. Part 2 is the Relay solver fill; poll status with `orderId ?? requestId`.

- **Relay owner-mutation quote deposit resolution.** Relay `/quote/v2` with `amount: "0"` may omit or zero `protocol.v2.paymentDetails`. When no deposit resolves, `buildOwnerMutationRelayFlow` re-quotes using `deriveRelayOwnerMutationDepositQuoteSeedWei`: seed = clamped zero-quote `fees.gas.amount` to `[MIN_OWNER_MUTATION_RELAY_DEPOSIT_WEI, MAX_OWNER_MUTATION_RELAY_DEPOSIT_SEED_WEI]` (8e12–0.0001 ETH), or MIN when `fees.gas` is absent/zero — no legacy 127× multiplier or gasPrice fallback. Resolve deposit via `resolveQuotedNativeDepositWei` (`paymentDetails`, `details.currencyIn.amount`, step value — ignore zero). Fail closed when no positive deposit; do not synthesize from echoed router value. `RELAY_API_KEY` is optional server-side (`x-api-key` on quote + notify only; status polling is unauthenticated).

- **Wake Relay solver after Part 1 confirms.** `ownerMutationExecution` calls `POST /api/relay/notify-deposit` (`/transactions/index` + `/transactions/single`) after Part 1 deposit confirms; notify failure is non-fatal — Part 2 may still complete via polling/`verifyMutation`. Relay `/transactions/index` expects the **bundle transaction hash**, not the AA UserOp hash — Base App `wallet_getCallsStatus` can return only the UserOp hash, so resolve the bundle tx via `eth_getUserOperationReceipt` in `resolveRelayPart1DepositTxHash.ts` before notify/index and on retries.

- **Relay has no official Discord.** Any server claiming to be Relay Discord is unofficial; integrator support paths are [radar.relay.link](https://radar.relay.link), support@relayprotocol.com, and [relayprotocol/relay-kit](https://github.com/relayprotocol/relay-kit) — do not reference a Relay Discord in runbooks or vendor asks.

- **Owner-install methods (Base App CSW direction)**: The validated, preferred path for Base App users is the **EntryPoint self-call** (`wallet_sendCalls` → single zero-value CSW self-call to `addOwnerAddress` → EntryPoint `handleOps`). This is the only shape that reliably satisfies `MultiOwnable.onlyOwner` because the wallet executes the call on itself. Real transactions confirmed this in 2026; attempts that put `addOwner` inside RelayRouter multicall fail the owner check exactly as expected. **`/add` tries this direct path first**; on Base App policy/funding/build failures (including misleading "not enough funds" when prefund passed), auto-fallback to **Relay Method A** via `shouldAttemptRelayMethodAFallback` + `executeAddOwnerRelayMethodA` — never on user rejections.

- **In Base App, Privy email OTP establishes the 4626 session but does not connect the Base Account signing provider.** Wallet execution surfaces (`/add` Method E, owner-install submit, sponsored swaps) need an explicit **Sign in with Base** / canonical CSW link — treat "logged into Privy but not Base" as a session misconfiguration, not an on-chain or Relay failure. `/add` EntryPoint owner-install gates on `ensureCanonicalBaseAccountWallet`: Base Account provider/`eth_requestAccounts` (or Privy Base Account wallet list) must match `profiles.csw_address` before submit. `/add` should surface definitive separate **4626 Privy session** vs **Base Account signing** status with working per-lane sign-out/disconnect — users repeatedly confuse the two.

- **Base App CSW UserOp owner-install requires CSW gas prefund before wallet review.** Base App often fails UserOp generation with "not enough funds" when the parent CSW has **0 native ETH and 0 EntryPoint deposit** (`EntryPoint.balanceOf(csw)` via `frontend/src/lib/wallet/cswEntryPointFunding.ts`). Preflight with `assessCswUserOpFunding` (~0.00005 ETH floor / ~0.0005 ETH recommended) on `/add` and block submit until funded — this is separate from Relay deposit semantics. **When prefund already passes, the same "Error generating transaction / not enough funds" copy is often Base App third-party UserOp policy block (misleading), not missing gas** — map via `mapAddOwnerFundingErrorMessage({ fundingPreflightOk: true })` and fall through to Relay Method A per the owner-install bullet above.

- **Passkey-first Base App Relay Part 1 preflight (Method B reference).** `cswSelfAuthOwnerDiscovery.ts` reads on-chain owner slots before Part 1: WebAuthn passkey at `owner[0]`, Base App session-key signer at `owner[2]`; ignore empty zero slots. Seed `submitSelfAuthRelayPart1SelfFunded` for session-key hash modes and `inner_secp256k1`. **Session-key Part 1 signing:** CSW `validateUserOp` checks the EntryPoint `userOpHash` — try that domain before replaySafe EIP-712 fallback; sign replaySafe via EIP-712 typed data (`CoinbaseSmartWalletMessage`), not raw `personal_sign` on the digest (Base App often surfaces misleading "not enough funds"). Base App may sign with a **delegated EOA** — `wallet_sendPreparedCalls` must use that recovered address in `signature.data`, not only `ownerAtIndex(2)`; prepared-calls signer candidates should try `session_key_delegated_eoa` before `owner_at_index`. When session-key ECDSA is structurally valid, **`validateUserOp` ecrecover preflight mismatch against `ownerAtIndex(2)` is advisory** — still submit via `session_key_prepared_calls_primary` or bundler; do not `continue` early or prompt a second sign. The `[preflightOwnerKeyMismatch]` console line is informational, not the failure. Fail fast only on **ephemeral substituted signers not in the CSW owner array** (`base app substituted signer not in csw owner array` / `baseAppOwnerInstallGuard.ts`). Prefer `eth_sendUserOperation` before prepared-calls; reject passkey (`owner[0]`) signatures for Part 1. Recipe: `docs/operations/base-app-session-key-relay-part1-recipe.md`. Historical Part 2 golden: `0x801b9d4b…91503` (passkey validates Part 2; inner add was session-key slot, not embedded EOA).

- **Relay Part 1 vs Part 2 use different CSW owner lanes (Method B).** Part 1 deposit UserOp = session key at owner slot 2; Part 2 solver fill = passkey `owner[0]` via `getUserOpHashWithoutChainId` (`org.toshi`). Part 2 landing alone does not prove embedded-EOA owner-install — gate on `isOwnerAddress(privyEmbeddedEoa)` and preview `addOwnerAddress(embeddedEoa)`.

- **Relay Part 1 may show only one internal tx.** When the CSW already holds EntryPoint prefund, Part 1 Basescan traces often show only `depositNative` (no separate prefund transfer) — that is normal, not a failed add-owner.

- **Relay owner-mutation status polling uses the deposit-bound id.** Poll `/intents/status/v3` with `orderId ?? requestId` from preview (`resolveRelayStatusRequestId`); treat Relay `status: unknown` as a stale quote; short-circuit and succeed on on-chain `verifyMutation` when Relay status lags. **Browser polling must not hit `api.relay.link` directly** — CSP `connect-src` blocks it; rewrite via `resolveRelayStatusFetchUrl()` to same-origin `GET /api/relay/intent-status` (Node scripts may still call Relay directly).

- **Automated Charm rebalance uses the protocol treasury Safe manager lane, not a bare KPR EOA or creator CSW delegate.** When Charm `manager()` is the protocol treasury Safe (`0x7d429e…`), keepers route `charmVault.rebalance()` through `executeViaProtocolTreasurySafe` (`frontend/server/_lib/wallet/protocolTreasurySafe.ts`, `kpr/utils/protocolTreasurySafe.ts`) so `msg.sender` is the Safe manager; signer resolution is `PROTOCOL_TREASURY_SAFE_OWNER_PK` → `KPR_PRIVATE_KEY` → `PRIVATE_KEY`, and the key must be an **EOA owner** on that Safe. Creator CSW `rebalanceDelegate` is for manual Base App rebalance; CSW UserOp automation applies only when the queue row CSW matches the delegate.

- **Zora-provisioned Coinbase Smart Wallets are owned by the Privy embedded EOA inside Zora's Privy app — NOT by the user's external Rabby/MetaMask EOA, and NOT necessarily by our app's Privy embedded EOA.** `CoinbaseSmartWallet.addOwnerAddress(address)` is `MultiOwnable.onlyOwner` (`msg.sender == address(this)`), so adding a new owner requires a self-UserOp signed by an existing owner — a plain `eth_sendTransaction` from any external EOA reverts, even if that EOA is "connected". Privy's Zora cross-app connect path was evaluated and rejected: Zora's provider accepts Connect handshake but refuses transact for our requester app, and the surfaced signer is not a CBSW passkey owner. Do not reintroduce "plain Base tx calling `addOwnerAddress`" language in UI copy or docs — it silently misleads users about what the flow actually does. The canonical in-app owner-install path is `POST /api/onboarding/preview-add-owner` → `useAddOwnerFlow` → `executeOwnerMutationViaRelay` (Relay deposit + solver fill; golden txs in `docs/_internal/operations/operations/wallet/relay-owner-mutation-kit-guide.md`); Zora iframe / deploy automation may still use `POST /api/onboarding/preview-agent-owner` and `POST /api/onboarding/provision-agent-owner` for the **server agent wallet**, not the login embedded EOA. Also: **never assume a Zora CSW needs an owner install just because it's Zora-linked.** Some users already have our app's Privy embedded EOA as an owner (from earlier direct flows); the install CTA must be gated on an on-chain `CoinbaseSmartWallet.isOwnerAddress(embeddedEoa)` check against `profiles.csw_address`, not on "Zora linked + CSW known."

- **Privy wallet lanes and embedded-EOA resolution.** Dashboard labels: key quorum → **4626 Server Agent Owner** (`PRIVY_WALLET_OWNER_ID`), policy → **4626 Agent Wallet Policy** (`PRIVY_WALLET_POLICY_ID`), server agent wallet → **4626 Agent Signer (server)** (never `4626.base.eth`), XMTP wallet → **4626 XMTP Agent Signer** — runbook: `docs/operations/privy-wallet-lanes.md`, rename script: `frontend/scripts/ops/rename-privy-wallet-labels.ts`. Login embedded EOAs stay policy-free; server agent wallets are automation-only.

- **Base App `/waitlist?setup=base-app` signing errors are pre-signing, not Relay reverts.** `Failed to fetch RPC request` / `An internal error was received` during **Enable 4626 signing** means `wallet_prepareCalls` failed before Coinbase's signing endpoint (`keys.coinbase.com`) — Relay Part 1 never ran and nothing hit chain. Remediation must **stay inside Base App** (force-close, reopen the link, confirm Base Mainnet, rebuild preview, retry once); do **not** tell users to open Chrome/Safari for this path. Coinbase Wallet in-app browser is a separate context where external-browser escape may still apply. Base App Relay Part 1 should prepare-first and must not cascade through alternate signing lanes on these RPC failures (avoids repeated passkey prompts).
