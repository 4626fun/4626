# Waitlist & Auth — ops & incidents

Cross-cutting operator prefs: [preferences-active.md](../preferences-active.md).
Parent index: [waitlist-auth.md](./waitlist-auth.md). **Read one sub-archive only** — do not load the full set.

- **Waitlist Airtable sync is historical / ops-only — not in the primary tree.** There is no live `/api/waitlist/airtable-sync` handler under `frontend/api` or `frontend/server/_lib/onboarding/` today; do not assume the cron route exists. When/if restored: it is an ops mirror, not account truth — cron-secret protected, writes Airtable from Supabase, must not rewrite points/referral ownership/wallet readiness/CSW/Privy/Telegram; merge keys stay `referral_conversion_id` / `signup_id` (legacy `canonical_wallet` / `profile:` backfill before upsert). `Personalized Onboarding Email` was an Airtable-owned `aiText` field, not API-writable.

- **`assertNoWalletPrivyCollision` must filter synthetic shells.** Emails matching `%@wallet.4626.fun` or `%@noemail.4626.fun` are pseudo-accounts (AMOE wallet-first claims, legacy wallet-login synthesis). They do NOT count as canonical — a real-email signup that shares a wallet with a shell must be allowed to proceed. The guard has this filter inline; do not remove it.

- **Wallet-collision queries that `ORDER BY p.id ASC` can pick the wrong profile when the same EVM address is attached to multiple live `profile_wallets` rows** — often stale merge-salvage rows on a lower `profile_id` stealing bootstrap/collision resolution from the true owner. Prefer verified-email/canonical-profile resolution over lowest-id wins; audit cross-profile duplicate addresses after merges; salvage sweeps must not leave one wallet on two real-email profiles (consider a live-profile uniqueness guard on `lower(address)`).

- **Email/profile collision ops:** run `pnpm -C frontend exec tsx scripts/diagnose-email-identity.ts --email=<addr>` to inspect profiles, aliases, wallet collisions, and orphan Privy rows before merge/repair — use this snapshot instead of ad hoc SQL alone.

- **Admin profile-merge lives at `POST /api/admin/profiles/merge`** with dual auth: admin session + `CRON_SECRET`. Dry-run by default; `{ mode: 'execute', confirm: 'MERGE-PROFILES' }` required to write. CLI operator: `pnpm -C frontend exec tsx scripts/merge-profiles.ts --from=<id> --to=<id>`. Merge primitive in `frontend/server/_lib/identity/profileMerge.ts` is idempotent per step; re-running is safe.

- **`walletSync.findExistingProfile` is alias-aware.** It consults `privy_user_aliases` before falling back to `profiles.privy_user_id`, mirroring `accountsIdentity.listProfileIdsForPrivyUser`. Without this, Rabby/EOA-first sign-in whose fresh Privy user id is aliased onto a canonical email-verified profile will create a new fragment instead of resolving back to the canonical row. Any future profile-lookup-by-privy-user-id code path must go through the alias cascade, not a direct `profiles.privy_user_id = ?` query.

- **Production host split is two SPA shells, not one.** On `4626.fun`, **`/` is rewritten to `public/immersive/index.html`** (not root `index.html`) via `frontend/vercel.json`; SPA routes like `/waitlist` and `/faq` still use marketing `index.html`. `https://app.4626.fun/*` serves `app.html` (Deploy, Portfolio, and other authenticated routes). **Marketing ↔ app must show the same canonical CSW:** waitlist applies `mergeCanonicalWaitlistAccount` from `/api/onboarding/bootstrap`; `useAccountMe` on `app.4626.fun` must use the same merge — do not let stale `profiles.csw_address` / session snapshots show a different address when navigating `4626.fun/waitlist` → `app.4626.fun/swap`. Favicon/brand fixes must include **`public/immersive/index.html`** and root `/favicon.ico` — partial deploys can leave marketing home stale while SPA routes already bumped `brandAssetVersion`. Privy email OTP and waitlist onboarding auth run only on React SPA routes (`/waitlist` → `WaitlistFlow`) — do not mount Privy on the static immersive home or duplicate auth there; marketing CTAs should link to `/waitlist?start=1` so Privy auto-opens on the SPA waitlist route. Base App mini-app `primary` URL should not bypass that marketing waitlist entry — setting primary URL only to `app.4626.fun` can skip the `4626.fun` immersive home and waitlist flow unless product explicitly wants app-only entry. Deploy/app deep links must use `https://app.4626.fun/...` — pointing users to the bare `4626.fun` host for `/deploy/vault` or similar authenticated routes is a recurring regression that silently lands them on the marketing shell. Auth uses the HttpOnly `cv_auth_session` cookie with `Domain=.4626.fun` on production hosts so sessions survive marketing-shell ↔ app-shell navigation; localhost/dev remains host-only, and session reads tolerate duplicate legacy host-only cookies during rollout. The canonical origin pair is documented in `frontend/.env.example` via `VITE_PRIVY_ALLOWED_ORIGINS` and `DEPLOY_SOLANA_REGISTRATION_ORIGINS`.

- **Waitlist UI must never synthesize a "full" state from missing stats.** `/api/waitlist/stats` returning null/500 or a zero capacity is an unknown state, not a "0 / 0 — Current round full" state. `frontend/src/features/waitlist/WaitlistFlow.tsx` must hide progress/urgency copy when stats are unavailable rather than fabricating a full-round banner — the "Current round full. Next approvals unlock the next batch." regression came from defaulting to 0/0 when the stats endpoint was 500ing.

- **Privy cross-app (Zora) linking must open its popup inside the click gesture.** Privy opens the Zora cross-app window with plain `window.open()`, which browsers only allow within the click's transient user activation. Waitlist `onLinkZora` calls `performZoraCrossAppAuth` synchronously on click and defers the access-token fetch, `/api/accounts/link`, and signal resolution until after cross-app auth completes — any awaited pre-work before the popup (e.g. a slow `/api/zora/resolve`) consumes the activation, the popup is silently blocked, and Privy shows its generic "Authentication failed" modal. This linking lane is read-only (Zora's provider shares the wallet read-only; no transact capability is requested).

- **Signer-gate consumers must source live Privy wallets from `useWallets()`, not from `extractPrivyWalletsFromUser(privyUser)`.** The `privyUser` object only carries `{ address, walletClientType }` metadata; the runtime provider state that the `privyEmbeddedEoaCanSign` / `canonicalSignerGate` logic needs (e.g. to know whether the embedded EOA is currently active and can actually sign) only surfaces through the `useWallets()` React hook. `frontend/src/pages/Swap.tsx` was the outlier — it derived the embedded-EOA signer from the metadata-only extraction and got stuck in `embedded-wallet-cannot-sign` even when the embedded EOA was already a confirmed owner of the canonical CSW — and has been switched to `useWallets()` as primary source (metadata extraction kept as fallback). `DeployVault.tsx` and `LaunchCoinCard.tsx` already followed this pattern. Any new page that gates on "can the embedded EOA sign right now?" must read from `useWallets()`, expose a recovery CTA that calls `setActiveWallet(embeddedWallet)`, and treat the metadata extraction as a snapshot-only fallback.

- **`zora-enable/` hosts single-file static HTML artifacts uploaded as Zora content coins (e.g. `agent install`, `feedback`, `signal`, `probe`).** These render inside an iframe on `https://magic.decentralized-content.com/ipfs/<cid>` **without** the `allow-same-origin` sandbox flag, which means: `localStorage` / `sessionStorage` / `document.cookie` all throw, `parent`/`top` are `SecurityError`, the Privy React SDK cannot run (it needs same-origin), WalletConnect's broadcast-channel plumbing frequently fails, and Cloudflare Insights/beacon scripts are blocked by Zora's `script-src-elem` CSP. Only EIP-6963 injected providers (Rabby, MetaMask, Coinbase Wallet extension, Brave) are reachable from inside. Zora's "Link" field on a content coin only accepts a fixed platform list: X, YouTube, TikTok, GitHub (gists work), Substack, Bluesky, Instagram, Farcaster, Wikipedia, Zora, Truth Social, Are.na, arXiv. Thumbnails are generated per-folder via `make-thumbnail.py`; `.glb` uploads require a separate raster thumbnail (Zora rejects `.glb` as its own thumbnail). Keep these artifacts sandbox-compatible — do not add dependencies that assume same-origin, React, Vite, or Privy. Because the sandbox blocks Privy/WalletConnect, the agent-install signing flow itself cannot live inside the Zora artifact — the content coin must only advertise + deep-link into the main `app.4626.fun` install page, which owns the actual `addOwnerAddress` transaction.

- **Production onboarding owner-preview depends on `PRIVY_WALLET_POLICY_ID`.** `createAgentWallet` in `frontend/server/_lib/wallet/privyWalletApi.ts` fail-closes in production when this env var is missing, which causes `/api/onboarding/preview-agent-owner` to error even before owner/install checks. Keep `PRIVY_WALLET_POLICY_ID` set on the live `4626-keepr-agent` service whenever rotating Privy config.

- **AlfaClub live auth uses a separate Privy app from 4626.** Orphan key quorums/wallets left in the 4626 Privy app from experiments are not wired to production AlfaClub chat; Privy API deletion of those quorums requires that quorum's original authorization key (not `PRIVY_WALLET_AUTHORIZATION_KEY` for the server agent owner).

- **The Virtuals ACP bridge is a separate Eliza plugin lane from the `/arena` dgclaw trading lane.** `frontend/server/agents/eliza/plugins/virtuals/` (`VirtualsAcpService`) drives the app.virtuals.io ACP agent via the `@virtuals-protocol/acp-node-v2` event-driven SDK. `VIRTUALS_ACP_AUTO_LLM` defaults off. High-risk `setBudget`/`fund`/`submit`/`complete`/`reject` decisions remain proposals unless explicitly authorized by the typed `VIRTUALS_ACP_EXECUTABLE_HIGH_RISK_TOOLS` list; spend args require positive numeric amounts and bounded caps, paid backtests require explicit positive payment amounts, and service-run global/per-job tool quotas default to 100/10. Run standalone with `pnpm -C frontend agent:virtuals` (never on the Railway Keepr primary); enable via `VIRTUALS_ACP_ENABLED=1` plus agent wallet/Privy-wallet-id/session-signer env. Runbook: `docs/_internal/operations/alfaclub/virtuals-acp-bridge.md`. The Arena degen.virtuals.io trading agent stays on `/arena` dgclaw + acp-cli.

- **AlfaClub chat bridge treats Cloudflare challenge failures separately from JWT/auth failures.** Cloudflare blocks should update the Cloudflare health/backoff path without marking the JWT as bad, triggering immediate Privy refresh, or opening the live-socket auth fallback in the same tick.

- **Railway Hermit liveness probes `/healthz`, not readiness.** Bootstrap (`frontend/server/agents/hermit/bootstrap.ts`) must return **200 on `/healthz`** during module load (Railway treats non-2xx as down); keep **`/readyz` at 503** until `index.ts` is up. `healthHandoff.ts` closes the bootstrap listener before the real health server binds — double-bind causes `EADDRINUSE` and stuck 503 forever. **Keep `/healthz` and `/readyz` off the DB hot path** — serve in-memory token-expiry snapshots and refresh AlfaClub JWT/Privy metadata via short-TTL background single-flight (`scheduleTokenExpiryRefresh` in `frontend/server/agents/hermit/index.ts`); never `await` Postgres reads on the probe response. Deploy via `railway.hermit.toml` → `frontend/Dockerfile.hermit`. **Railway CLI auth:** `RAILWAY_TOKEN` must be an account API token from [railway.com/account/tokens](https://railway.com/account/tokens) (long string), not a 36-char project/service UUID; on WSL when `railway login` cannot open a browser, use `railway login --browserless`.

- **`svix` must stay pinned to CJS-compatible `uuid` resolution.** To prevent Vercel runtime failures in `@privy-io/server-auth` (`svix` requiring ESM-only `uuid@14`), keep `svix>uuid` overridden to `10.0.0` in both root and frontend package overrides.

- **Privy XMTP signer must not silently trust stale owner-index hints.** `frontend/server/_lib/wallet/privyXmtpSigner.ts` resolves owner index with `allowConfiguredOwnerIndexFallback: false`; invalid `CANONICAL_CSW_OWNER_INDEX` values are treated as advisory and ignored in `eliza/index.ts` so runtime auto-detects the actual owner slot.

- **Known split Phase-1 batchers can reject nonzero salt overrides.** `0xe3F9490CfD6bd3D68010405d18Bf772C167E7178` and `0xF941Bb68e4f083f3F531cc598d5C08d0b8FfbA7E` may revert phase-1 calls with `SaltOverrideDisabled()` (`0xe7fdf838`), so deploy planners/session builders must avoid nonzero share salt overrides. Server-side stale-payload normalization must keep the same `...WithSalt` selector family and zero only the override argument; rewriting to an unsalted selector can hit missing entrypoints on deployed batchers.

- **Waitlist wagmi mount must defer hook consumers one commit.** `WalletProviders` wraps children in `DeferWagmiConsumers` via `useDeferUntilAfterCommit()` so wagmi `Hydrate` reconnect does not trigger setState-during-render warnings on waitlist setup surfaces.

- **Privy-returned counterfactual smart-wallet addresses must not overwrite `profiles.csw_address`.** The persisted canonical CSW remains the deployed Zora/Coinbase Smart Wallet; bootstrap/wallet-sync paths should preserve it when Privy exposes an undeployed smart-wallet candidate with no Base code, and use Privy wallets (including Zora-app Privy smart-wallet candidates) as signer identities rather than promoting them to the asset-holding CSW. All persistence must go through `resolveStoredCanonicalCswAddress` in `frontend/server/_lib/wallet/canonicalCswPersistence.ts` — allowed-owner EOAs and undeployed candidates must never be written as `profiles.csw_address`.

- **DeployVault session gating must treat the parent-CSW + Privy embedded-owner path as deploy-capable after session restore.** Do not require a separate wagmi smart-wallet connection before showing deploy controls when the canonical CSW and embedded owner signer are already available.

- **Wrong external EOA stuck as MAIN WALLET is a profile sync artifact, not CSW identity.** A one-off wagmi connect can persist `profiles.primary_wallet` / `profile_wallets.is_primary` for an external Rabby/MetaMask EOA while canonical CSW + Privy embedded owner stay correct — use account tray **Disconnect main wallet**, or `pnpm -C frontend exec tsx scripts/fix-stale-external-primary-wallet.ts --email=… --apply` (`disconnectExternalWalletFromProfile`), then reconnect the intended wallet; do not treat the stale EOA as the canonical asset-holding account. When a canonical CSW + embedded signer exist, `walletSync` should keep `primary_wallet` on the embedded EOA via `resolveProfilesPrimaryWalletColumn`, not a transient wagmi extension that `COALESCE` would freeze forever.

- **`GET /api/accounts/me` requires `X-Privy-Token`.** Ad-hoc browser `fetch('/api/accounts/me', { credentials: 'include' })` without Privy headers returns `Missing Privy auth token`; use `useAccountMe` / `apiFetch` with `getAccessToken`, or `GET /api/auth/me` for the HttpOnly session snapshot only.

- **`useAccountMe` must not cache null/failed responses.** Only cache successful `/api/accounts/me` payloads; retry when Privy token becomes available and bootstrap-fallback execution signals when track is `none-yet` but on-chain owner is confirmed. `canonicalSignerGate` should not return `execution-setup-required` when `ownerCheckStatus === 'owner'` even if server track lags.

- **The built-in Grep / codebase-search tooling is unreliable in this workspace** — it frequently returns zero matches for strings that demonstrably exist (even common ones like `waitlist`). Fall back to `rg` (ripgrep) via the shell, and **scope the search path** (e.g. `frontend/src`, `frontend/server`) because an unscoped `rg` over the repo root hangs/scans `node_modules` and large build dirs. This recurs across many sessions.

- **`/api/rpc` proxy (`frontend/api/_handlers/rpc/_proxy.ts`) routing rules:** the proxy is session-authenticated (unauthenticated reads → **401**; **403** = signed in but upstream rejected). `ENV_RPC_FAILOVER_STATUS = {401,403,404,405,426}` makes it skip a rejected upstream and try the next env/public Base RPC; `RETRYABLE_STATUS = {429}`. Rejected env RPC URLs are **negative-cached ~15 min** so a dead provider only logs once. Because of failover, most `/api/rpc` calls still return **200** even when an env RPC is down — treat upstream-fallback warn logs as noise, not outages. Deploy dry-run reads the local Anvil fork (`http://127.0.0.1:8545`) directly instead of the auth-gated proxy.

- **Waitlist X-engagement implementation (`waitlistTwitterEngagementConfig.ts`).** Active step order is env-driven: no campaign tweet → `['follow']`; with `WAITLIST_X_ENGAGEMENT_TWEET_URL`/`_TWEET_ID` → `['follow','retweet','comment']`. On-demand verify uses `verifyEngagement.ts` (follow: 1-page `/following` max 1000 + cached `@4626fun` id; repost/comment: capped user timeline). Like step intentionally omitted. Webhook at `/api/x/account-activity/webhook` auto-awards follow via `follow_events` and can also award retweet/comment via `tweet_create_events`; on-demand Verify complements the webhook. Idempotent `x_engagement_*` point sources shared with POST verify path. Each active step = **4 XP**.

- **X MCP (`xapi`) wiring for Cursor:** configure in gitignored `.cursor/mcp.json` with `pnpm dlx @xdevplatform/xurl mcp` — **not** `npx`, because npm chokes on this monorepo root `package.json` pnpm-only override keys (e.g. `@arbitrum/nitro-contracts>@openzeppelin/contracts`). Register `http://localhost:8080/callback` in **X Developer Portal** OAuth 2.0 app (not Vercel) for local `xurl`/MCP login — distinct from Privy waitlist callbacks. MCP reads OAuth2 `CLIENT_ID`/`CLIENT_SECRET` from `mcp.json` (distinct from OAuth 1.0a `X_*` in `frontend/.env`). `xurl` requests all scopes hardcoded in its source — portal subset grants cause authorize **400**; inject portal OAuth2 tokens into `~/.xurl` or enable all requested scopes. OAuth2 env var names must not contain dots — use `X_ACCESS_TOKEN_OAUTH2` / `X_REFRESH_TOKEN_OAUTH2`, not `X_ACCESS_TOKEN_2.0`. - **Embedded-EOA private keys must never be server-exported.** There is no smooth in-app path to extract a Privy embedded EOA's raw key, by design — key export is allowed only client-side via Privy with explicit user consent, and **Zora's** embedded EOA cannot be exported from 4626 at all (only from Zora/Zora CLI with the user in the loop). The affirmed lane for Zora CSW creators stays: 4626 creates its **own** Privy embedded EOA (signer), the user connects their EOA, and that 4626 embedded EOA is added as an **owner** of the Zora Coinbase Smart Wallet — 4626 owns the signer, the Zora CSW stays the custody/identity anchor. Do not pursue server-side key handoff or CLI key-import workarounds.

- **Auth request-storm root cause:** an unstable Privy access-token getter (`useSafePrivyAccessToken()` / `privy.getAccessToken?.bind(privy)` returning a new function each render) retriggers effects in `WaitlistFlow` / account hooks → bursts of `/api/auth/me`, `/api/accounts/me`, `/api/waitlist/x-engagement` calls → **429** (`/api/auth/me` is 180 req/min/IP). Fix by stabilizing the token getter with `useCallback` and honoring `Retry-After` 429 backoff in the shared session/`useAccountMe` caches; the bootstrap/accounts handlers also use dual per-Privy-session + per-IP rate limits.

- **Stale compiled `.js` twins in `frontend/server/` and `frontend/api/` can shadow `.ts` sources in Vitest** (module resolution picks `.js` first) — when rate-limit, deploy-session, or keeper tests fail mysteriously after `.ts` edits, delete orphaned `.js` artifacts beside the `.ts` sources and re-run the suite.

- **Deploy session `POST /api/deploy/v2/session/status` is a pure DB read** — onchain/DB advancing lives in `_advanceCore.ts` and is reachable only through explicit `session/resume`, not the public status poll route (H2-03 remediation).

- **Waitlist/auth production 500s after identity migrations:** when deployed Vercel code still SELECTs dropped `profiles.primary_smart_wallet` or expects dropped `public.wallets` / `public.referral_clicks`, `/api/accounts/me`, `/accounts/link`, `/waitlist/bootstrap`, and `/waitlist/leaderboard` fail before user lookup — Vercel logs show `waitlist_schema_migration_required:…` from `ensureWaitlistSchema`; `/api/health` can stay 200. Align `frontend/server/` + API handlers to `csw_address` and the post-migration schema, then deploy — not a DB connectivity outage.

- **Returning-wallet sign-in false "account not found":** `WaitlistReturningWalletSignIn` ("Sign in with linked wallet") shows "No account found for this wallet" / "Account not found" when `/api/waitlist/bootstrap` returns 500 — the schema guard aborts before wallet lookup, so existing EOAs look missing. Fix bootstrap first; email OTP uses the same bootstrap path and can fail the same way until deploy catches up.

- **`usePrivyOAuthReturnBackendSync` retry storm:** while backend is unhealthy, 429/5xx/401/403/recovery failures on `/accounts/link` must not reset the OAuth sync attempt flag — otherwise Privy return hooks hammer `/accounts/link` and amplify 429 rate limits on top of the underlying schema 500s.

- **Local deploy dry-run dev (`pnpm -C frontend run dev:deploy-dry-run`):** serves on **port 5174** (not 5173) with local fixed code against prod Supabase — behavior can differ from 4626.fun until production deploy matches. - **Zora cross-app `oauth/link` on waitlist localhost needs app-client credentials, unlike plain email OTP.** OTP works app-id-only, but `POST auth.privy.io/api/v1/oauth/link` 401s `"Missing auth token"` without a `privy-client-id` header. Fix: `resolveWaitlistLoopbackPrivyClientId()` sends `VITE_PRIVY_CLIENT_ID` on loopback when `VITE_PRIVY_CLIENT_ID_ENABLED=1`, `mode="waitlist"` configures `crossApp: { providerAppIds: [ZORA_PRIVY_APP_ID] }`, and `loopbackSessionMarkerShim.ts` re-asserts the `privy-session` marker on reload after the Zora OAuth redirect (it was clearing even with a persisted `localStorage` session). Also required in the Privy dashboard on the **same client** as `VITE_PRIVY_CLIENT_ID`: explicit **Redirect URLs** (not just Allowed Origins) for each `http://localhost:<port>/waitlist` / `127.0.0.1` variant in use — Origins alone don't cover OAuth return. Any session created before enabling the client id is app-id-only and must be cleared (sign out + re-verify email) before `oauth/link` will succeed. `zoraCrossApp.ts` treats `"Missing auth token"` as recoverable (retry via login) and falls back to read-only `/api/zora/resolve` if link ultimately fails. Default Privy `walletList` re-initializing WalletConnect Core on every Strict Mode mount (`Init() was called N times` console spam) is fixed by using an empty wallet list on waitlist email-OTP (no Coinbase/WC on that path), not a real error.

- **Waitlist wallet-return sign-in must keep `PrivyClientProvider` on stable `mode="waitlist"`.** Signing in with an existing external EOA (`WaitlistReturningWalletSignIn`) creates the 4626 session cookie; remounting or mutating Privy into a deleted dual-mode (`waitlist-email-only` / `waitlist-wallet-joined`) can drop `privy.authenticated` even though the waitlist UI still shows the user as signed in — clicking **Link X** then fails with `"Sign in before linking an account"` from `assertPrivyAuthenticated`, even though the 4626 session is fine (another `4626 session != Privy session` case). Fix: keep a single `mode="waitlist"` provider (remount only the returning-wallet **runner** via `key={walletSignInAttempt}`); `Link X` also falls back to opening Privy's Twitter login directly if Privy still isn't authenticated instead of hard-failing.

- **The Privy localhost marker-cookie assertion pattern (`loopbackSessionMarkerShim.ts`) must be applied at every Privy SDK call site, not just token reads — this is a recurring root cause, not a one-off.** `providerLink.ts`'s `unlinkPrivyProvider`/`linkPrivyProvider`, `WaitlistFlow.tsx`'s Zora `unlinkCrossAppAccount` call, and `privyAuthorizedWalletRpc.ts`'s `postAuthorizedWalletRpc` (used by XMTP `personal_sign`/`eth_signTypedData_v4`) each 401'd on localhost until they asserted the `privy-session` marker immediately before the SDK call, matching the working `refreshPrivyEmbeddedSignerSession` pattern. A 401 on one Privy call (e.g. editing a linked identity) can trigger `resetPrivyLoopbackSessionAfterAuthFailure()`, wiping the whole local session and cascading into an unrelated-looking XMTP connect failure moments later — make sure `/api/v1/siwe/unlink` (not just `siwe/link`) is in the 401-reset matcher. Separately, Privy's `unlinkWallet`/`unlinkTwitter` SDK methods take plain strings, not `{ value }` objects, and Twitter unlink needs the Privy **subject**, not the display handle.
